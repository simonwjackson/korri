# Dev-Lab / Theme-Workshop: Architecture Research Notes

> Generated by repo-analyst · 2026-07-03  
> Scope: `tools/theme-workshop/` — how the canonical design tool actually works as built.

---

## (a) Overview

The **dev-lab** (`just dev-lab`, port 3130) is a dev-only Vite SPA that renders
real product surfaces at physical device size without ever bundling into
`product/apps/*`. It is NOT a prototype gallery or a Storybook replacement: it
renders the actual product components through their actual wiring; the only
thing the tool changes is *which data is fed in at the edge*.

Governing principle (from `tools/theme-workshop/AGENTS.md`):

> The tool is the product app **unwrapped**; production is the same app
> **wrapped**. The one and only thing allowed to differ is the data, swapped at
> the last-mile edge.

Two legacy aliases remain for the same Vite config:
- `just dev-theme-workshop` → prints a deprecation warning and starts dev-lab
- `just dev-lab-device` → sets `LAB_DEVICE=1` and starts dev-lab (phone/tablet
  HMR-reconnect variant)

Three surface adapters are registered in `surface-registry.ts`:
1. **shift** — fully migrated to real-edge / parts-own-edges model
2. **pico** — migrated to part-first model but retains one preview singleton
   (`pico-data-preview.ts`) for its Data axis
3. **boxbuster** — legacy; no part-first migration yet

### Core architecture files

#### `lab/lab-router.tsx`

TanStack Router v1 setup. Route tree:
- `/` → `LabIndexRedirect` — redirects to `/lab/all/<defaultAdapter>/`
- `/lab/$devices/$themeId/$` (splat) → `LabRoute`

`buildLabPath(devicesSegment, themeId, surfacePath)` constructs all URLs.
`LabRoute` reads params, delegates to `<LabRoot routeState=... navigation=...>`.

The `devicesSegment` encodes which physical devices are selected (comma-separated
ids or `"all"` or `"none"`). `themeId` selects the surface adapter. `surfacePath`
drives the mounted surface's in-process `MemoryHistory` — only the live surface
router navigates when the user picks a screen; the outer URL stays at the lab.

#### `lab/lab-route-state.ts`

Pure parsing/serializing utilities for the URL segments:

- `parseDeviceSegment` → `DeviceSelection ({ kind: "all" } | { kind: "set"; ids })`
- `selectedDevicesForSegment` → resolved id list
- `normalizeSurfacePath` / `surfacePathToSplat` — normalize leading slashes

#### `lab/LabRoot.tsx`

**The calibration + context wiring root.** Responsibilities:
1. Finds the adapter from `labSurfaceAdapters()` by `routeState.themeId`
2. Loads `LabCalibrationState` from `localStorage` (`lab-<adapterId>:lab`) — contains `pxPerMm`, device roster, knob values
3. Calls `adapter.makeSeedInitialValues()` async to get the mount-time atom seed
4. Constructs `LabContextValue` and provides it via `<LabContext.Provider>`
5. Renders `<LabShell />` once both are ready

`LabCalibrationState` is persisted after every mutation (`patchDevice`,
`addDevice`, `removeDevice`, `setKnob`, `reset`). Calibration storage key is
`lab-<adapterId>` (distinct from the legacy `theme-workshop` namespace to avoid
inheriting stale state).

The `/parts` path alias is handled here: `partsAlias = (requestedPath === "/parts")` → the context always receives `"/"` for the surface path in that case; the Parts panel is shown via the URL segment, not a separate route.

#### `lab/Lab.context.tsx`

```ts
interface LabContextValue {
  adapter: LabSurfaceAdapter     // the active surface adapter
  initialValues: unknown         // atom seed array from makeSeedInitialValues()
  themeId: string                // active adapter id
  surfacePath: string            // the currently-visible route inside the surface
  screens: LabSurfaceScreen[]    // screens the surface declares
  selection: DeviceSelection     // which devices the URL says are selected
  devices: DeviceConfig[]        // calibration roster
  selectedDevices: DeviceConfig[] // filtered to selection
  pxPerMm: number                // calibrated px-per-mm
  knobValues: Record<string, number>  // theme generator knob state
  calibration: LabCalibrationController  // mutation callbacks
  setDevicesSegment / setThemeId / setSurfacePath  // URL-updating navigations
}
```

`useLab()` throws if called outside `LabRoot`. Every sub-component reads from
here instead of prop drilling.

#### `lab/LabShell.tsx`

**The main workspace component.** Manages all runtime state that belongs to one
session of a given surface:
- `catalog`: `LabPartsCatalog | null` — loaded by `loadSurfacePartsResult(adapter.id)` on adapter change
- `generatedTakes`: AI/recipe takes not yet in the static catalog
- `aiPartStories`: runtime-loaded AI-authored parts from `ai-takes/`
- `objects`: `LabCanvasObject[]` — the canvas (live device objects + placed part objects)
- `selectedObjectId`: selected canvas object
- `previewSelection`: pick-mode inner part selection
- Axis controller state (delegated to `useLabAxisController`)

Key derived state:
- `catalogWithGenerated` — the story index used for canvas rendering (includes un-promoted takes)
- `partsCatalog` / `partsIndex` — the Parts panel catalog (source-backed parts + promoted takes only)
- `screenInputs` / `screenEvents` — resolved via `deviceInputsForScreen` / `deviceEventsForScreen` (part-scoped, falling back to legacy screen-scoped)

**Inspector routing logic** (in `LabShell` render):
```
previewSelection && selectedPreviewObject?  → <LabPreviewInspector>  (picked inner part)
selectedLiveObject?                         → <LabDeviceInspector>   (live device axes + inputs + events)
selectedPlacedObject && story?              → <LabObjectInspector>   (placed part bindings)
(nothing selected)                          → hint text
```

**Chrome is adaptive**: viewport width determines whether the chrome renders as
`LabBarChrome` (wide, floating/docked panels) or `LabOverlayChrome` (narrow,
sheet-based). User can override; choice is persisted. Four standard panels:
Devices, Parts, Inspector (state), Design (intrinsic-design sliders). Optional
Controls panel if `adapter.useControls` is set.

#### `lab/surface-registry.ts`

Defines `LabSurfaceAdapter` — the product bridge interface — and the three
registered adapters. Key fields:

| Field | Purpose |
|-------|---------|
| `id` | String identifier (`"shift"`, `"pico"`, `"boxbuster"`) |
| `devices` | Canonical device roster for this surface |
| `screens` | `LabSurfaceScreen[]` with `label`, `path`, optional `pagePartId` (stable design-part id) |
| `axesForScreen(path)` | Returns `LabStateAxis[]` for a route — state machines the screen exposes |
| `captureCoordinate(path)` | Reads current live state into a `LabScreenCoordinate` (for "Pin current") |
| `inputsForScreen(path)` | **Legacy fallback only.** Screen-scoped held inputs. Not set on Shift. |
| `eventsForScreen(path)` | **Legacy fallback only.** Screen-scoped discrete events. Not set on Shift. |
| `surfacePartInputs(story)` | **Part-scoped** held inputs — the migrated path. Returns inputs for a given part story. |
| `surfacePartEvents(story)` | **Part-scoped** discrete device events keyed by part story. |
| `partRegistryRoot` | `ComponentType<LabPartRegistryRootProps>` — the surface's own part registry root (e.g. `ShiftPartSurface`) |
| `surfacePartMount(story, binding)` | Returns `LabSurfacePartMountSpec | null` — the atom seed + real subtree for live mounting a placed part |
| `renderSurfacePart(story, binding)` | Static/prop-driven render fallback for parts with no live mount spec |
| `previewScope(children)` | Wraps parts in the surface's CSS scope when needed (pico only — adds `[data-pico].pico-screen.intrinsic` wrapper at 640×480) |
| `makeSeedInitialValues()` | Async: builds the atom seed array for a full surface mount |
| `mountSurface(host, options)` | Imperative mount: renders the full surface into an HTML element |

#### `lab/LabSurfaceMount.tsx`

**The live device mount host.** Imperatively mounts one surface:

1. Creates a `MemoryHistory` starting at `surfacePath`
2. Calls `adapter.mountSurface(host, { initialValues, history, dualScreen, onRegistry })`
3. The `onRegistry` callback receives the mounted surface's `AtomRegistry`;
   `registerLabSurfaceRegistry({ scopeId, registry, seed })` stores it in the
   global `lab-surface-registries` hub so axes can write to it
4. Subscribes to `history` — pushes outbound navigations (user clicks a link
   inside the surface) to `onNavigate`; receives inbound navigations (the lab
   changes surfacePath) by pushing to `history`
5. Cleanup: `unregisterRegistryRef`, `mounted.dispose()`, `history.destroy()`

The `scopeId` parameter is the canvas object id, so an axis can target one
device's registry specifically via `eachLabSurfaceRegistryForScope`.

`seedMapFromInitialValues` converts the `[Atom, value][]` array to a `Map` that
the registry entry records as the mount-time seed.

### Adapters directory (`lab/adapters/`)

**Shift adapter** (`shift.ts`, `shift-axes.tsx`, `shift-edges.ts`, `shift-surface-part.tsx`):

- `shiftLabSurfaceAdapter` in `shift.ts` assembles the full adapter. Declares two screens: `{ label: "Home", path: "/", pagePartId: SHIFT_DESIGN_PARTS.home.id }` and `{ label: "Game Detail", path: "/game/hollow-knight" }`. No `inputsForScreen`/`eventsForScreen` (fully migrated).
- `shift-axes.tsx`: Declares `shiftLibraryAxis` (id `"data"`, kind `"single"`, swaps `catalogFactsSourceLayerAtom`) and `shiftActiveGameAxis` (id `"foreground"`, kind `"single"`, swaps `foregroundSessionStatusLayerAtom`). Both use `eachTargetRegistry` to write into the correct scope. `shiftCaptureCoordinate` reads current state via `readShiftCurrentCoordinate`.
- `shift-edges.ts`: `shiftSurfacePartEvents(story)` — Home and Status Bar get battery+network events; Battery gets battery only. `shiftSurfacePartInputs(story)` — Status Bar gets clock input; Home gets foreground select + clock input. Clock input's `apply`/`release` write/restore `shiftClockIsoAtom` in the scope's registry.
- `shift-surface-part.tsx`: `shiftSurfacePartMount(story, binding)` returns the atom-seed array + real subtree for Battery, Status Bar, and Home. Uses `ShiftBatteryFromDeviceState` (reads `deviceStateAtom` → `shiftPowerDisplayForDeviceState`) and `ShiftStatusBarFromEdges` (reads `deviceStateAtom`, `shiftClockIsoAtom`, `shiftNetworkReadingAtom`). Home seeds 8 atoms including catalog layer, foreground layer, library source, launcher. `reseedKeys` array ensures only changed inputs re-write the registry (event-driven facts don't roll back). `renderShiftSurfacePart` handles Library Variant parts (prop-driven from `shiftLibraryGamesForBinding`).

**Pico adapter** (`pico.ts`, `pico-axes.tsx`, `pico-edges.ts`, `pico-surface-part.tsx`):

- Fully migrated to `surfacePartMount` / `surfacePartEvents` / `surfacePartInputs`.
- `picoAxesForScreen`: Still uses the `pico-data-preview.ts` singleton — `pin = pinFromTable(picoDataStateSamples, setPicoDataPreview)`, `release = () => setPicoDataPreview(null)`. This is the **one remaining preview singleton** (transitional debt; Shift no longer uses it).
- `previewScope`: Pico wraps parts in a `[data-pico].pico-screen.intrinsic` div (640×480) so container queries resolve without a full mount.
- Exposes `useControls: usePicoControls` — the optional surface-owned controls panel.

**Boxbuster adapter** (`boxbuster.ts`):

- No `partRegistryRoot`, no `surfacePartMount`, no `surfacePartInputs`, no `surfacePartEvents`.
- Screens declared but no `pagePartId` (label-matching only).
- Legacy `setBoxbusterArtMode("offline")` called on mount to prevent external art calls.
- Does not implement `axesForScreen` or `captureCoordinate`.
- **Least-migrated surface.**

### Part-mount directory (`lab/part-mount/`)

#### `LabPartMount.tsx`

The placed-part live mount host. Single responsibility: mount one part through
the surface's `partRegistryRoot` and keep the registry live across binding
changes **without remounting**.

```
LabPartMount({ Root, spec, bindingKey, scopeId })
  ├─ renders <Root initialValues={spec.initialValues} onRegistry={handleRegistry}>
  │    └─ spec.node   (the real subtree, e.g. <ShiftHomeFromEdge />)
  └─ on bindingKey change (NOT initial mount):
       ├─ compare spec.reseedKeys[i] vs previous
       └─ re-write only changed atom pairs into the SAME live registry
```

`handleRegistry` fires when the registry is created (immediately on mount); it
calls `registerLabSurfaceRegistry({ scopeId, registry, seed })`. The `seed` is
the initial atom values, held in `seedRef` and never updated — it is the
mount-time baseline that `release` restores to.

The `reseedKeys` granularity prevents, for example, rotating the clock input
from also rolling back a battery event that was fired while the clock was being
edited.

### Seed directory (`lab/seed/`)

#### `shift-seed.ts`

Builds the `SeedInitialValues` array (8 atom-value pairs) for a full Shift mount:

- `catalogFactsSourceLayerAtom` → catalog derived from a real ProseQL in-memory library
- `librarySourceLayerAtom` → in-memory library source
- `launcherLayerAtom` → `makeInMemoryLauncherLayer({ behavior: { kind: "succeed" } })`
- `foregroundSessionStatusLayerAtom` → `shiftForegroundSourceLayers.Ready()`
- `shiftPowerReadingAtom` → default power reading
- `deviceStateAtom` → seeded from the default power reading (so the battery renders before any battery event)
- `shiftClockIsoAtom` → default ISO timestamp
- `shiftNetworkReadingAtom` → default network reading

`makeSeedInitialValuesForBinding(binding)` additionally branches on `sourceId` to
choose a fixture library and on `stateId` to select a catalog source layer — so
the live device objects can pre-seed different data states at mount time.

### Parts discovery (`lab/parts-discovery.ts`)

`surfacePartModules()` calls `import.meta.glob("./**/*.part.tsx")` (defined in
`product/surfaces/web/parts-glob.ts`). This is the **compile-time part
discovery** — Vite resolves the glob at build time. AI-authored parts in
`ai-takes/` are explicitly excluded here and loaded separately at runtime via
`GET /__lab/ai-parts/:surface`.

`loadSurfacePartsResult(surfaceId)` filters by `parsePartPath` (regex:
`/...\.{atom,molecule,organism,template,page}\.part\.tsx$/`), loads each module
async, and merges with `storiesFromDesignPass(activeDesignPass, surfaceId)`.

Part file convention: `<Name>.<layer>.part.tsx` where layer ∈
`{atom, molecule, organism, template, page}`.

Story export conventions:
- `default` → component function or StorySpec (with `name`, `state`, `render`, `designPartId`, `presentation`, etc.)
- Named PascalCase exports → additional components (each becomes a story)
- Arrays of StorySpec → related state variants (auto-linked via `variants` field)
- `rootProps`, `classNames`, `name`, `note`, `surface`, `designPartId` → module-level metadata (reserved, not treated as stories)

`buildStoryIndex` collapses state-variant families (linked via `variants`) to
one representative per family in the tree (resting state priority: ready > idle
> live > default > loaded > success).

### `useLabAxisController.ts`

**Owns the page-axis lifecycle.** Extracted from `LabShell` so the ordering
contract lives in one place and is independently testable.

```
useLabAxisController(adapter, scopeId?) → {
  screenAxes, activeByAxis, mode, pinAxis, liveAxis, pinCurrent, toggleMode
}
```

Key behaviors:

- `screenAxes` — finds the first screen with axes in `adapter.axesForScreen`; axes belong to the live surface, not to part selection.
- `mode` — derived: `"inspect"` if any axis has a pin; `"live"` if all are live.
- `pinAxis(axisId, stateId)` — for `multi`: toggles off if already pinned. Calls `axis.pin(stateId, axisContext)`, then `applyAxisMap`.
- `liveAxis(axisId)` — calls `axis.release(axisContext)`, then `applyAxisMap`.
- `applyAxisMap(next)` — loop: release any nested axis no longer `axisEnabled` (prevents stale pins on greyed-out axes), then `setScopedActiveByAxis`.
- `toggleMode()` — Live→Inspect: restores remembered pins via `restorePinsActive`; Inspect→Live: remembers current pins, releases all.
- `pinCurrent()` — calls `adapter.captureCoordinate(activeScreenPath)`, maps the coordinate to `LabAxisActive` values, applies them. Only exposed when `adapter.captureCoordinate` exists.
- Cleanup `useLayoutEffect` on `[adapter, activeScreenPath]` change: releases all axes and clears all per-scope state.

Scope logic: `scopeKey = scopeId ?? "__global__"`. `axisContext = scopeId ? { scopeId } : {}`. Active and remembered maps are keyed by scope, so two live device objects can independently have different pins.

### Device-lab kit (`tools/theme-workshop/device-lab/`)

A self-contained, template-agnostic physical-calibration harness. Reusable
standalone; the dev-lab imports it for device sizing and screen normalization.

#### `DeviceLab.tsx`

Standalone component for designs that don't use the full lab infrastructure.
Owns `LabState { pxPerMm, devices, knobs }` in `localStorage`. Renders
`DeviceFrame` per device and a `Calibrator`. The dev-lab's `LabRoot` / `LabShell`
replicate this logic (not import it) because the dev-lab has additional
multi-screen, multi-object, adapter, and registry concerns.

#### `DeviceFrame.tsx`

Converts `widthMm × heightMm × pxPerMm` → exact `widthPx × heightPx`. Draws
an optional bezel (padding = 3.7% of height, radius = 4.7% of height). When
`maxHeightPx` is set and `outerH > maxHeightPx`: **display-only
`transform: scale(fit)` applied to the bezel, NOT the screen div** — the
`.lab-screen` keeps its true pixel dimensions so container queries resolve
exactly as on the real device. Only the painted output shrinks. `fit` stored in
`data-fit` attribute for debugging.

The `lab-screen` div carries `container-type: size` so any child using `cqi`/`cqh`
units resolves against the physical screen size.

#### `Calibrator.tsx`

Three-tab panel (Devices / Scale / Generators):
- **Devices**: per-device name, W mm, H mm inputs; add/remove
- **Scale**: ISO ID-1 credit-card overlay (85.6 × 53.98 mm) + range slider for `pxPerMm` (2.5–9, default 3.7795 = 96 dpi nominal)
- **Generators**: theme knob sliders (base, ratio, space, etc.)
- **Export**: copies calibration NDJSON to clipboard

Collapses to a floating `⚙` FAB when closed. State (open/tab) persisted per
`storageKey`.

#### `device-screens.ts`

`deviceScreens(device)` — normalizes any device to `ScreenConfig[]` (single-screen
devices yield a synthetic primary screen from their own `widthMm`/`heightMm`).

`groupScreensByPlacement(screens)` — splits screens into `{ primary, above, below, left, right }`.

`clusterBoundingHeightPx(screens, pxPerMm)` — total painted height for scale-to-fit;
above/below screens stack, left/right screens compete with the primary's height.

## (c) Key Data-Flow Narratives

### Narrative 1: Axis pin changing a live device's state (Inspect mode)

1. User selects a live device canvas object (sets `selectedObjectId`)
2. `LabShell` shows `<LabDeviceInspector axes=screenAxes ...>`
3. User changes the Data axis dropdown to "Empty"
4. `LabDeviceInspector` calls `onPin("data", "Empty")`
5. `LabShell.pinAxis("data", "Empty")` → `useLabAxisController.pinAxis`
6. Controller calls `axis.pin("Empty", { scopeId: selectedLiveObjectId })`
7. `shiftLibraryAxis.pin` in `shift-axes.tsx`:
   - `make = shiftCatalogSourceLayers["Empty"]` → calls `make()` to get a fixture layer
   - `eachTargetRegistry({ scopeId })` → iterates `lab-surface-registries` entries matching that scope
   - `registry.set(catalogFactsSourceLayerAtom, layer)` — writes into the mounted surface's real atom registry
8. The Shift Home route's `useAtomValue(catalogSnapshotAtom)` re-derives from the new source layer
9. The component tree re-renders showing the Empty catalog state
10. Controller updates `activeByAxis` → `mode` becomes `"inspect"` → `data-lab-mode="inspect"` on the shell

### Narrative 2: Placed part on the Compose board — live mount + binding edit

1. User clicks "Home · Ready" in the Parts panel
2. `LabShell.selectStory(storyId)` → `setSelectedIds([...prev, storyId])`
3. `reconcileInstancesWithSelection` creates `LabPlacedPartObject { storyId, sourceId, inputValues }`
4. `LabWorkshopBoard` renders `<LabDraggablePart instance=... story=...>`
5. `LabDraggablePart.renderBody()`:
   - `adapter.surfacePartMount(variant, { sourceId, inputValues })` → returns `LabSurfacePartMountSpec`
   - Renders `<LabPartMount Root={ShiftPartSurface} spec=... bindingKey=... scopeId=instance.id>`
6. `LabPartMount` mounts: `<ShiftPartSurface initialValues=spec.initialValues onRegistry={handleRegistry}>`
7. `handleRegistry(registry)` → `registerLabSurfaceRegistry({ scopeId: instance.id, registry, seed })`
8. `spec.node` renders (e.g. `<ShiftHomeFromEdge />`) — reads atoms from the fresh registry
9. **User edits the "Foreground" input to "Playing"** via `LabObjectInspector`
10. `LabShell.bindObjectInputValue(id, "foreground", "Playing")` → updates `object.inputValues`
11. `LabDraggablePart` re-renders with new `inputValues` → new `bindingKey`
12. `LabPartMount` effect fires: compares `reseedKeys`, finds foreground key changed
13. Only the foreground atom pair is re-written: `registry.set(foregroundSessionStatusLayerAtom, layer)`
14. `ShiftHomeFromEdge` re-renders with the updated foreground state
15. Clock/battery/network atoms in the same registry are **unchanged** — event-driven facts survive

### Narrative 3: Device event (battery changed)

1. User selects a live device, sees `<LabDeviceInspector>` with Events section
2. User edits the battery payload (percent=10, charging=false) and clicks "Send"
3. `LabShell.emitLiveDeviceEvent(deviceObjectId, "battery", payload)`
4. `emitScopedEvent(screenEvents, deviceObjectId, "battery", payload)`:
   - `event.emit(canonical, { scopeId: deviceObjectId })`
5. `shiftDeviceEvents()[0].emit(...)` in `shift-edges.ts`:
   - `state = shiftDeviceStateForPowerReading(shiftPowerReadingForValue(payload))`
   - `eachLabTargetRegistry(scopeId, ({ registry }) => registry.set(deviceStateAtom, state))`
6. Shift Home re-renders: `deviceStateAtom` → `shiftPowerDisplayForDeviceState` → battery props

### Narrative 4: Inner-part pick mode (preview selection)

1. User enables pick mode in toolbar
2. `LabInspectableContent` wraps every canvas object's rendered content
3. User clicks on the Status Bar atom inside a Home page object
4. `handlePointerDownCapture` → `previewSelectionFromEventTarget(event.target, scopeId)`
5. DOM walk up from `event.target` reading `data-korri-part` attrs written by `LabPreviewBoundary`
6. Returns `LabPreviewSelection { scopeId, targets: [statusBarTarget, homeTarget], activeIndex: 0 }`
7. `LabShell.selectPreviewPart(selection)` → sets `previewSelection`, sets `selectedObjectId=scopeId`
8. Inspector shows `<LabPreviewInspector>` with Status Bar's part-scoped inputs/events
9. Highlight overlay rect computed from the DOM element's `getBoundingClientRect` relative to the object

## (d) Open Debt / Rough Edges

### 1. Pico preview singleton (known, documented, transitional)

`product/surfaces/web/pico/pico-data-preview.ts` is the last surviving
`preview ?? live` pattern. Pico's Data axis still drives a cross-root singleton
(`setPicoDataPreview(null|result)`) that the live pico routes consult, rather than
swapping a source layer atom via the real registry. This is:
- Production-inert (guarded by `preview ?? live`)
- A tool-only side channel that bypasses the real wiring
- Explicitly tracked in `lab-boundary.test.ts` (it asserts the file exists,
  as a reminder to remove it once migration completes)

**Fix**: follow the Shift pattern — replace `setPicoDataPreview(result)` with
`registry.set(catalogFactsSourceLayerAtom, catalogLayer)`.

### 2. Boxbuster is not migrated

`boxbusterLabSurfaceAdapter` has no `partRegistryRoot`, no `surfacePartMount`,
no `surfacePartInputs`, no `surfacePartEvents`, and no `axesForScreen`.
The surface renders but the Inspector for a live device has no axes, no part
inputs, no events. Parts placed on the Compose board render via the static
`story.render()` bake. Pick mode does nothing because `LabPreviewBoundary`
produces no `data-korri-part` attrs in the static render.

### 3. Live device state dials are shared, not per-object (current known limitation)

From `lab/AGENTS.md`:
> Live-device state dials and screen inputs are shared across live device objects
> for now, matching the mounted surface registry model.

Pinning Data to "Empty" on device A also pins it on device B. The axis
controller does scope when a `scopeId` is passed (`useLabAxisController` takes
`scopeId` and the `axisContext` is scoped accordingly), but `LabShell` only passes
`selectedLiveObjectId` — so the axes only track per-scope while one device is
selected, but `eachLabSurfaceRegistry` (unscoped) was the original path for some
writes. Current state: axis `pin`/`release` is scoped to the selected device,
but there's no per-device independent state across devices simultaneously visible.

### 4. AI-generated parts are validate-and-write, not type-checked

Parts written to `ai-takes/` pass only:
- `export default` present
- All imports in a hard-coded allowlist (`PART_IMPORT_ALLOWLIST`)

They are excluded from the repo typecheck (`tsconfig.json` presumably has an
`exclude` for `ai-takes/`). A bad type-unsafe file can silently produce a broken
preview without a build error.

### 5. `LabScreenFrame` vs `DeviceFrame` divergence

`LabScreenFrame` (Compose board, placed parts) and `DeviceFrame` (device-lab kit,
live devices) are separate implementations with different sizing contracts.
`LabScreenFrame` is aspect-ratio only (no mm→px, no bezel) because placed parts
are "device-agnostic". This is intentional but means a placed part's visual size
at any given zoom level is disconnected from physical millimetres.

### 6. Parts-discovery and design-pass `activeDesignPass` is statically imported

`active-design-pass.ts` exports `activeDesignPass` at module load time — it is
not dynamically per-surface. If multiple surfaces could have concurrent design
passes, this would need to be per-surface or per-adapter.

### 7. Canvas placement is global, not per-adapter

`lab-canvas-placement.ts` uses a fixed `PLACEMENT_CELL` size for all placed
parts regardless of their natural screen size. Parts that render at very
different aspect ratios overlap. `placeNext("grid", ...)` avoids previously
placed rects but uses the same cell size for both the new part and the occupied
list, so a tall part placed next to a wide part may still collide.
