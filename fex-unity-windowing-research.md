# Research: FEX-Emu graphics/windowing behavior for x86_64 Linux games on ARM64

## Summary
FEX graphics acceleration depends on native-library thunking: keep CPU execution in x86_64, but forward graphics/windowing libraries such as GL, Vulkan, X11, drm, and sometimes wayland-client to host ARM64 libraries. For Unity Linux games, the safest first path is usually X11/Xwayland + Vulkan/GL/drm thunks, with SDL forced to `x11`; native Wayland/SDL2 paths have known crash/no-window reports, and Gamescope historically captures Xwayland clients more reliably than Wayland clients.

## Findings
1. **Enable FEX graphics thunks explicitly per app, not globally first.** FEX documents `ThunksDB` app configs such as `$HOME/.fex-emu/AppConfig/<AppName>.json` with `{ "ThunksDB": { "GL": 1, "Vulkan": 1 } }`; recent examples for GPU acceleration also include `drm` and `Config.ThunkConfig` pointing at `/usr/share/fex-emu/ThunksDB.json`. This is the primary knob to test through `FEX_APP_CONFIG` or app-specific config files. [FEX thunk setup](https://wiki.fex-emu.com/index.php/Development:Setting_up_Thunks), [FEX Config](https://wiki.fex-emu.com/index.php/Config), [FEX discussion #5303](https://github.com/FEX-Emu/FEX/discussions/5303)
2. **Bundled guest Vulkan loaders can prevent FEX Vulkan thunking.** FEX wiki game notes say removing a game-shipped `libvulkan.so.1` lets Vulkan thunks work, and Transport Fever 2 is noted as shipping its own Vulkan loader, causing Vulkan thunking not to work. For Unity games, inspect the game directory before assuming FEX is reaching the host Turnip loader. [Jupiter Hell - FEX wiki](https://wiki.fex-emu.com/index.php/Jupiter_Hell), [Transport Fever 2 - FEX wiki](https://wiki.fex-emu.com/index.php/Transport_Fever_2)
3. **X11 is a core part of the current accelerated path.** FEX release notes state X11 is required for both Vulkan and OpenGL thunking in the DXVK/Proton path, and later FEX releases redirected the X11 `Display` object directly in OpenGL/Vulkan to reduce thunk complexity. This makes `SDL_VIDEODRIVER=x11`/Xwayland a high-priority control case before testing native Wayland. [FEX 2209](https://fex-emu.com/FEX-2209/), [FEX 2405 release mirror](https://www.linuxcompatible.org/story/fex-release-fex2405-released/)
4. **Wayland-client thunking exists but should be treated as the experimental branch.** FEX 2310 added early wayland-client thunk wiring, enough for a Super Meat Boy + Wayland + Zink override case, but the wording is explicitly early support. Do not make Unity success depend on this path until the X11 path is characterized. [FEX 2310](https://fex-emu.com/FEX-2310/)
5. **SDL has two independent levers: dynamic replacement and video backend selection.** SDL's dynamic API can redirect a statically/dynamically linked game to a chosen SDL library with `SDL_DYNAMIC_API=/path/to/libSDL2-2.0.so.0`, while `SDL_VIDEODRIVER=x11` or `wayland` forces the windowing backend. This allows controlled tests with the game SDL versus host/known-good SDL and X11 versus Wayland. [SDL dynapi](https://wiki.libsdl.org/SDL3/README-dynapi), [SDL2 video driver hint](https://wiki.libsdl.org/SDL2/SDL_HINT_VIDEODRIVER), [SDL2 FAQ](https://wiki.libsdl.org/SDL2/FAQUsingSDL)
6. **Unity + Vulkan + native Wayland has independent crash evidence.** SDL issue #8780 reports a Unity 2019 Vulkan game crashing when forced to `SDL_VIDEODRIVER=wayland`; SDL issue #8909 also tracks older/X11-designed games crashing when switched to Wayland. This lines up with a hypothesis that Unity failures under FEX may be window-system/WSI selection, not only CPU emulation. [SDL issue #8780](https://github.com/libsdl-org/SDL/issues/8780), [SDL issue #8909](https://github.com/libsdl-org/SDL/issues/8909)
7. **FEX has Unity-specific non-graphics failure history too.** FEX issue #3347 for ULTRAKILL describes a Unity game creating no window and crashing under FEX/Turnip, with discussion pointing at a possible Unity GC problem; FEX signal-handling issue #1682 says Unity depends on graceful handling of asynchronous signals and SIGSEGV/null-pointer behavior. If X11/SDL/Vulkan experiments do not change symptoms, collect signal/GC evidence rather than staying only in graphics. [FEX issue #3347](https://github.com/FEX-Emu/FEX/issues/3347), [FEX issue #1682](https://github.com/FEX-Emu/FEX/issues/1682)
8. **Gamescope is mainly an Xwayland control surface unless Wayland-client exposure is deliberately enabled.** Gamescope issue #543 says SDL2 Wayland clients were not captured by Gamescope while `SDL_VIDEODRIVER=x11` made Gamescope work; related notes say newer Gamescope may force X11 unless an expose-Wayland option is used. This makes Gamescope useful for isolating Xwayland behavior, but not a neutral test of native Wayland. [Gamescope issue #543](https://github.com/ValveSoftware/gamescope/issues/543), [steamtinkerlaunch Gamescope notes](https://github.com/sonic2kk/steamtinkerlaunch/wiki/GameScope)
9. **Turnip/Freedreno is the correct Adreno Vulkan target, but FEX thunk version must match modern Vulkan extension expectations.** Mesa documents Turnip as the Vulkan 1.3 driver for Adreno 6xx; FEX 2601 updated Vulkan thunks to Vulkan 1.4.337 because newer Mesa/DXVK/VKD3D-Proton extension exposure could assert before the update. Pinning FEX/Mesa together matters when testing Adreno. [Mesa Freedreno docs](https://docs.mesa3d.org/drivers/freedreno.html), [FEX 2601 release](https://github.com/FEX-Emu/FEX/releases/tag/FEX-2601)

## Actionable next experiments
1. **Baseline app config matrix:** create a per-game `FEX_APP_CONFIG` JSON with `GL`, `Vulkan`, and `drm` enabled; run once with only `Vulkan+drm`, once with `GL+drm`, and once with all three. Log `FEX_OUTPUTLOG=stderr`/verbose FEX config if available, `VK_LOADER_DEBUG=all`, and `LIBGL_DEBUG=verbose`.
2. **Force the Xwayland path first:** run the Unity game with `SDL_VIDEODRIVER=x11`, unset Wayland-only overrides, and launch under a known Xwayland host. If Gamescope is used, treat it as the Xwayland compositor/control path and record whether Gamescope creates/captures the window.
3. **Then test native Wayland as a separate branch:** run `SDL_VIDEODRIVER=wayland` only after the X11 path is known. Try a `ThunksDB` entry for wayland-client only if FEX's installed ThunksDB exposes it; otherwise do not assume it exists from the config name.
4. **Control SDL linkage:** run with the game-shipped SDL, then with `SDL_DYNAMIC_API=/path/to/known/libSDL2-2.0.so.0`. Pair each with `SDL_VIDEODRIVER=x11` and `wayland` to separate SDL ABI/backend problems from FEX graphics thunking.
5. **Remove/rename bundled Vulkan loaders for one test:** if the game directory contains `libvulkan.so`, `libvulkan.so.1`, Vulkan ICD JSONs, or bundled Mesa/Vulkan layers, move them aside in a disposable copy and re-run with `VK_LOADER_DEBUG=all` to confirm the ARM64 host Turnip ICD is selected through FEX thunking.
6. **Turnip sanity check outside Unity:** run a tiny x86_64 Vulkan sample under FEX with the same app config and display environment. If it fails, fix FEX/Vulkan/Turnip first; if it passes, move to Unity-specific signal/SDL logging.
7. **If no-window persists across X11 and Wayland:** collect `strace -f -e signal,openat,connect`, Unity `Player.log`, FEX stderr, and coredump backtrace. Compare for Unity signal/GC failures noted in FEX issues rather than chasing WSI only.

## Gaps
FEX's current installed `ThunksDB.json` should be inspected locally to confirm exact thunk keys for `wayland-client`/`WaylandClient`, `X11`, and `drm`; web search did not provide a complete current key list. The research also did not confirm a single Unity 2019 root cause under FEX: graphics WSI, bundled loaders, SDL backend, and Unity signal/GC handling all remain plausible until the matrix above is run.
