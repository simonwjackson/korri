# Research: Steam Linux client local observability surfaces

## Summary
Steam on Linux exposes useful local observability, but most of it is a mix of human-readable rolling logs plus Valve Data Format (VDF/ACF) state files rather than a stable public API. For an embedded appliance, the most actionable strategy is to discover the Steam root and library folders, tail selected logs under `logs/`, parse `steamapps/appmanifest_<appid>.acf` and `config/libraryfolders.vdf`, and treat appinfo/workshop/cloud/shader files as corroborating state rather than a single source of truth.

## Findings
1. **Steam root and library discovery should be dynamic** — The common native-client root is `~/.local/share/Steam`, with `~/.steam/steam` and `~/.steam/root` commonly resolving there; Valve bug reports and log bundle instructions also use `~/.steam/steam/logs`. Flatpak/Snap or custom installs can move this root, and Steam libraries can live anywhere listed in `config/libraryfolders.vdf`, so an appliance should resolve symlinks and parse library folders instead of hard-coding one path. [ValveSoftware/steam-for-linux issue showing `~/.steam/steam/logs`](https://github.com/ValveSoftware/steam-for-linux/issues/12299) [ValveSoftware/steam-for-linux bootstrap path issue](https://github.com/ValveSoftware/steam-for-linux/issues/9347)

2. **Primary lifecycle logs live in `logs/` and are useful for event capture** — Keep these as first-class capture points: `content_log.txt` for app/depot download, install, validation, staging, and update activity; `shader_log.txt` for shader pre-cache activity; `bootstrap_log.txt` for Steam client bootstrap/update; `console_log.txt` and `console-linux.txt` for client stdout/console messages and launch-related noise; `appinfo_log.txt` for app metadata/appinfo refreshes; `workshop_log.txt` for workshop item downloads/updates; `cloud_log.txt` for Steam Cloud sync; `compat_log.txt` for compatibility-tool/Proton integration; `connection_log.txt`/network logs for CDN/connectivity context. Valve issue logs list these exact files under Linux Steam log bundles, including `.previous.txt` rotations. [ValveSoftware/steam-for-linux issue #7870](https://github.com/ValveSoftware/steam-for-linux/issues/7870) [ValveSoftware/steam-for-linux issue #11243](https://github.com/ValveSoftware/steam-for-linux/issues/11243) [ValveSoftware/steam-for-linux issue #9659](https://github.com/ValveSoftware/steam-for-linux/issues/9659)

3. **`appmanifest_<appid>.acf` is the best app-level machine-readable install/update checkpoint** — For every installed or queued app, inspect each library's `steamapps/appmanifest_<appid>.acf`. Useful fields commonly include `AppID`, `name`, `installdir`, `StateFlags`, `LastUpdated`, `LastPlayed`, `SizeOnDisk`, `buildid`, `UpdateResult`, `BytesToDownload`, `BytesDownloaded`, `BytesToStage`, `BytesStaged`, and `MountedDepots`. `StateFlags` is widely used by Steam tooling but is not a formally documented public contract; parse it as a bitfield with tolerant fallbacks and corroborate with `content_log.txt` and directory state. [SteamCMD - Valve Developer Community](https://developer.valvesoftware.com/wiki/SteamCMD) [steam-appmanifest README example](https://github.com/pinkwah/steam-appmanifest/blob/master/README.md)

4. **Download/install directories expose coarse state even when manifests lag** — Per library, watch `steamapps/downloading/<appid>/` for active downloads, `steamapps/temp/` for staging/temporary files, `steamapps/depotcache/` for depot chunks, and `steamapps/common/<installdir>/` for installed payload presence. SteamPipe’s public docs describe builds as depots and manifests, which matches the client’s depot/build terminology in app manifests and content logs. Use these directories as supporting evidence, not as authoritative completion signals, because Steam can preallocate, stage, validate, or clean asynchronously. [Steamworks Builds documentation](https://partner.steamgames.com/doc/store/application/builds) [Steamworks depot search result](https://partner.steamgames.com/doc?q=depot)

5. **App metadata is available locally but not always convenient to parse** — `appcache/appinfo.vdf` and `appcache/packageinfo.vdf` hold cached Steam metadata and can explain names, launch configs, branches, depots, and package ownership, but modern `appinfo.vdf` is effectively binary/serialized Steam data rather than simple text VDF. Prefer existing parsers or treat it as an optional enrichment source; do not block lifecycle detection on it. `logs/appinfo_log.txt` is often a safer text signal that metadata refreshed. [ValveSoftware/steam-for-linux issue listing `appinfo_log.txt`](https://github.com/ValveSoftware/steam-for-linux/issues/7870)

6. **Workshop and cloud have separate state surfaces** — Workshop content usually appears under `steamapps/workshop/content/<appid>/`, with download/staging paths under `steamapps/workshop/downloads/` and app-level workshop state in `steamapps/workshop/appworkshop_<appid>.acf`; pair this with `logs/workshop_log.txt`. Steam Cloud local state is app/user-specific, commonly involving `userdata/<account_id>/<appid>/remote/` and `remotecache.vdf`, with sync activity in `logs/cloud_log.txt`. Capture these separately from base app install state so workshop/cloud delays do not falsely mark the base app as still installing. [ValveSoftware/steam-for-linux issue listing `workshop_log.txt` and `cloud_log.txt`](https://github.com/ValveSoftware/steam-for-linux/issues/9659)

7. **Shader pre-cache is observable but loosely coupled to app install** — Watch `logs/shader_log.txt`, library/global shader cache directories such as `steamapps/shadercache/<appid>/`, and `content_log.txt` for downloads that are shader/precache-related. On Linux/Steam Deck-like systems shader pre-caching may happen after app install or before launch, may be disabled by user/client settings, and may not be required for launch readiness; expose it as a separate `shaderPrecache` status rather than folding it into `installed`. [ValveSoftware/steam-for-linux issue listing `shader_log.txt`](https://github.com/ValveSoftware/steam-for-linux/issues/11243)

8. **Launch lifecycle has no single stable per-app event file** — Launch attempts are visible through `console_log.txt`, `console-linux.txt`, `compat_log.txt`, Steam runtime/Proton output, and sometimes crash/minidump directories. For Proton titles, setting launch options such as `PROTON_LOG=1 %command%` can emit `$HOME/steam-<appid>.log`, but that is opt-in and noisy, not a default appliance signal. The Steam process launched from CLI often just forwards a request to the running client, so process exit alone is not proof that the game started or stopped. [ValveSoftware/Proton FAQ](https://github.com/ValveSoftware/Proton/wiki/Proton-FAQ) [Steam community Proton log guidance](https://steamcommunity.com/app/221410/discussions/0/3276824488728677951/)

9. **Command/IPC surfaces are good for triggering actions, weak for observing them** — `steam -applaunch <appid>` and `steam steam://rungameid/<appid>` can request launches; `steam://open/console`/Steam console can expose internal commands for manual diagnosis; SteamCMD supports scripted `app_update`-style installs, but SteamCMD state is not the same as the interactive client’s full UI/session state. For appliance observability, treat command output as an initiating trace and observe completion through files/logs. [SteamCMD - Valve Developer Community](https://developer.valvesoftware.com/wiki/SteamCMD)

10. **Recommended appliance capture plan** — At startup: resolve Steam root, enumerate `libraryfolders.vdf`, map `appid -> library/appmanifest`, and snapshot `logs/*.txt` offsets. During operation: `tail -F` selected logs, inotify `appmanifest_<appid>.acf`, `libraryfolders.vdf`, `downloading/<appid>`, `shadercache/<appid>`, `workshop/appworkshop_<appid>.acf`, and `userdata/*/<appid>/remotecache.vdf`. Derive states as an ADT: `Unknown`, `NotInstalled`, `Queued`, `Downloading`, `Staging`, `Verifying`, `Installed`, `UpdateRequired`, `ShaderPrecacheActive`, `Launching`, `RunningUnconfirmed`, `LaunchFailed`, `CloudSyncing`; always include source evidence and last-seen timestamp.

## Gaps
- Valve does not appear to publish a stable, complete schema for `appmanifest_<appid>.acf` state transitions or `StateFlags`; validate observed values against the appliance’s Steam client version.
- `appinfo.vdf` parsing details vary by Steam client version and parser library; test any parser against real appliance data before relying on it.
- Launch start/stop confirmation remains the weakest area without integrating process/session supervision outside Steam; pair Steam logs with the appliance’s own process/session tracking where possible.
