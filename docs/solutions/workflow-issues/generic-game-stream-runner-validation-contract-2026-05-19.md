# Validate the generic game stream runner with a fresh launch intent per session

## Context

The generic game stream runner was validated from an external NixOS streaming host using the local Korri checkout. The architecture under test was intentionally generic:

1. A trusted local controller writes a pending `LaunchSpec` intent.
2. Moonlight launches one stable Sunshine app, `Korri Stream`.
3. Sunshine runs the Korri runner as the foreground app command.
4. The runner consumes the pending intent, launches that process, and exits when the process exits.

Several confusing issues surfaced during that validation. Most were not runner bugs; they were contract and environment misunderstandings around flake consumption, Sunshine service scope, Sunshine app identity, and the one-shot nature of the launch intent.

## Guidance

### Keep remote flakes stable, override locally for development

External consumers should point at the remote Korri flake in committed config:

```nix
korri = {
  url = "github:simonwjackson/korri";
  inputs.nixpkgs.follows = "nixpkgs";
};
```

For fast local development, override the input at command time:

```bash
nixos-rebuild build \
  --flake .#<host> \
  --override-input korri path:<path/to/local/korri>
```

In the consuming NixOS repo, this belongs in a generic flake-override workflow rather than Korri-specific Just recipes. For example, a wrapper can accept repeatable `--override-input NAME VALUE` flags and pass them to both flake host discovery and `nixos-rebuild`. Machine-local persistence belongs in ignored local env, for example:

```bash
export NIXIE_EXTRA_ARGS="--override-input korri path:<path/to/local/korri>"
```

The committed flake can then keep using GitHub while one developer's machine uses the local checkout.

### Check Sunshine as a user service, and `korri-server` in its configured scope

On the validated NixOS host, Sunshine was installed as a systemd user service. This command failed with exit code `4` because there was no system unit:

```bash
systemctl status sunshine
```

Use the user service instead:

```bash
systemctl --user status sunshine --no-pager
journalctl --user -u sunshine -b -f
```

When checking remotely:

```bash
ssh <host> 'systemctl --user status sunshine --no-pager'
```

Note: Sunshine remains a user service in both `services.korri.server.serviceMode` modes. `korri-server` itself depends on the configured scope:

- `serviceMode = "user"` (default) -> `systemctl --user status korri-server`
- `serviceMode = "system"` (e.g. headless stream hosts) -> `systemctl status korri-server`

See the pattern doc [boot-scoped control plane with session-scoped runner via shared private runtime dir](../architecture-patterns/boot-scoped-control-plane-with-session-scoped-runner-2026-05-19.md) for the lifecycle split.

### Trust the generated Sunshine app file, not stale user app JSON

The active Sunshine configuration pointed at a generated Nix apps file:

```text
file_apps=/nix/store/...-apps.json
```

The user's `~/.config/sunshine/apps.json` still contained older Desktop / Steam examples. That file was not the active app source for the Nix-managed service. Confirm the active apps from the configured `file_apps` path or from Nix evaluation, not from stale user config.

The generated app list contained two different entries with different meanings:

- `Korri Stream` — the generic foreground runner app. This is the one to launch for the launch-intent flow.
- `Korri Stream Profile` — a profile/desktop-style app generated by the host streaming profile. It can connect to the desktop but does not exercise the generic runner.

### Enqueue first; launch second

The runner expects a pending intent at the configured path. The exact path depends on which `services.korri.server.serviceMode` the host is using:

- **User mode** (default): `$XDG_RUNTIME_DIR/korri-game-stream/next-launch.json`
- **System mode** (headless stream hosts): `/run/korri-game-stream/next-launch.json`

The runner wrapper exports `KORRI_GAME_STREAM_RUNTIME_DIR`, `KORRI_GAME_STREAM_INTENT_PATH`, and `KORRI_GAME_STREAM_STATUS_PATH` baked in by the module so the runner converges on the same directory the server uses. When enqueuing manually, set `KORRI_GAME_STREAM_INTENT_PATH` to match the host's effective path.

A valid test sequence (user mode):

```bash
cmd=$(nix build nixpkgs#supertux --no-link --print-out-paths)/bin/supertux2

KORRI_GAME_STREAM_INTENT_PATH="$XDG_RUNTIME_DIR/korri-game-stream/next-launch.json" \
  korri-game-stream-enqueue -- "$cmd"
```

System-mode hosts use the absolute path instead:

```bash
KORRI_GAME_STREAM_INTENT_PATH="/run/korri-game-stream/next-launch.json" \
  korri-game-stream-enqueue -- "$cmd"
```

Then launch `Korri Stream` from Moonlight.

The intent is one-shot after a successful session launch. Recoverable startup failures may requeue the claimed intent, while malformed or stale intents are quarantined. If the user quits the game or stops the Moonlight session and immediately tries to launch `Korri Stream` again, the runner is expected to fail until another intent is enqueued.

For that no-intent case, the runner returns a preflight failure to Moonlight but intentionally does not overwrite the previous runtime status file. If `status.json` still shows the prior clean exit, that means the stream app is wired correctly enough to run the runner, but the controller step was skipped.

### Prefer the Korri CLI for known library games

For a known Korri library game, the human-facing controller is the Korri CLI:

```bash
korri stream launch
korri stream launch <game-id>
korri play --host http://<host>:3001
```

The CLI talks to the `korri-server` RPC; the server is the component that writes the launch intent and that may run as either a user service or a system service. The Sunshine-launched runner still needs to share file ownership with the server (same Unix user), which the NixOS module enforces. The command prepares a fresh one-shot foreground launch intent from the existing Korri library and then stops; the next manual step is still launching `Korri Stream` from Moonlight.

Use the lower-level `korri-game-stream-enqueue` path for raw command validation, non-library targets, per-game display environment experiments, and lifecycle/wait-monitor validation. The product CLI intentionally does not expose session lifecycle flags in its first slice.

### Keep the validation target generic

Do not validate the generic runner by turning Sunshine into a per-game launcher, and do not enqueue Steam unless the explicit test is Steam. The point of this path is that Sunshine knows only about one stable foreground app and the runner launches an arbitrary structured `LaunchSpec`.

A good smoke target is a Nixpkgs game with a realized store path:

```bash
cmd=$(nix build nixpkgs#supertux --no-link --print-out-paths)/bin/supertux2
KORRI_GAME_STREAM_INTENT_PATH="$XDG_RUNTIME_DIR/korri-game-stream/next-launch.json" \
  korri-game-stream-enqueue -- "$cmd"
```

This respects the contract better than configuring Sunshine with a game command or treating Steam as the default validation path.

Some games need display backend hints. Put non-secret per-game display overrides in the launch intent rather than hard-coding them into Sunshine:

```bash
korri-game-stream-enqueue \
  --env SDL_VIDEODRIVER=wayland \
  -- /run/current-system/sw/bin/nix run nixpkgs#supertux -- --fullscreen

korri-game-stream-enqueue \
  --env DISPLAY=:0 \
  -- /run/current-system/sw/bin/nix run nixpkgs#extremetuxracer
```

Do not place credentials or long-lived secrets in `LaunchSpec.env`; pending and quarantined intent files are local diagnostic artifacts.

### Prefer `status.json` when output logs are missing

The module config may set Sunshine app output to:

```text
$HOME/.local/state/korri/game-stream-runner.log
```

During validation, that file did not exist even though the runner was executing and status was being written. Use the runtime status file as the primary low-friction diagnostic. The path depends on `serviceMode`:

```bash
# user mode
cat "$XDG_RUNTIME_DIR/korri-game-stream/status.json"

# system mode
cat /run/korri-game-stream/status.json
```

Sunshine's user journal remains useful for confirming whether the app command started, whether the client connected, and whether the foreground command exited.

## Why This Matters

The generic stream runner is deliberately not a remote arbitrary command listener and not a Sunshine-per-game configuration layer. Its safety and portability come from a narrow lifecycle boundary:

- a trusted local actor writes one launch intent;
- Sunshine starts one stable runner app through Sunshine pairing/authentication on a trusted network or VPN;
- the runner completes the intent after a successful session launch, requeues recoverable startup failures, and quarantines malformed/stale intents;
- foreground runner exit lets Sunshine end the active app/session.

If validation skips the enqueue step, inspects the wrong Sunshine service scope, or launches the profile app instead of the runner app, the failures look like stream or runner defects even though the contract is working. Capturing the exact workflow keeps future validation focused on real integration gaps rather than re-debugging expected one-shot behavior.

The one-shot behavior also explains why the Korri CLI exists: repeated Moonlight-only launches need a controller that prepares a fresh intent before each launch. Replaying stale intents by default would weaken the trusted-intent model.

## When to Apply

- Wiring `services.korri.gameStream` into an external NixOS host.
- Testing `Korri Stream` from Moonlight after a local NixOS switch.
- Seeing immediate `Korri Stream` disconnects after a previous successful session.
- Validating local Korri changes from another flake before the remote Korri branch has been pushed or locked.
- Deciding whether a failure belongs in Sunshine config, host deployment, local controller workflow, or the runner itself.

## Examples

### Correct end-to-end smoke sequence

```bash
# 1. Confirm Sunshine user service is running.
ssh <host> 'systemctl --user status sunshine --no-pager'

# 2. Prepare a fresh intent for a known Korri library game.
ssh <host> 'korri stream launch <game-id>'

# 3. Launch the Sunshine app named "Korri Stream" from Moonlight.
# 4. Quit the game.
# 5. Enqueue again before launching "Korri Stream" again.
```

### Immediate disconnect after quitting once

```bash
ssh <host> 'cat "$XDG_RUNTIME_DIR/korri-game-stream/status.json"'
```

If the status still shows the previous session, for example:

```json
{
  "mode": "exited",
  "runId": "previous-run",
  "exitCode": 0
}
```

then the no-intent launch did not create a new status observation. The next action is not to restart Sunshine. Enqueue a new intent and launch `Korri Stream` again.

### Distinguish the two Moonlight entries

```text
Korri Stream          -> generic runner; requires a pending launch intent
Korri Stream Profile  -> host display/profile app; useful for desktop/capture validation, not runner validation
```

### Local flake override in the consuming repo

```bash
just build <host> --override-input korri path:<path/to/local/korri>
```

If the consuming repo wraps `nixie`, prefer a generic `--override-input` pass-through over one-off `korri-local-*` recipes. One-off recipes solve the immediate problem but do not compound for the next local flake input.
