Swapping the layer-atom seam

Layer 2 is the only role you touch to change behavior in tests and Storybook. This lesson shows the two ways Korri overrides a layer atom — and why the runtime, data atoms, and components stay completely untouched.

~9 minutes   Mission goal: "modify a UI surface using a swappable Layer seam"

Prereq: Lesson 0001 (the five roles). If "layer atom" and "runtime atom" aren't crisp yet, replay 0001 first or open reference/effect-atoms-glossary.html.

Why the seam works at all

Recall the runtime atom from 0001 — it reads its layers with get(...): 

export const libraryRuntime = Atom.runtime(get =>
  Layer.merge(get(librarySourceLayerAtom), get(launcherLayerAtom)),
)

Because librarySourceLayerAtom is a writable atom that merely holds a Layer, replacing its value makes the runtime rebuild, which makes libraryItemsAtom re-run with the new implementation. Nothing downstream changes. The component still calls useAtomValue(libraryItemsAtom) and has no idea which layer it got.

This is the bedrock rule made concrete: the seam for swapping data sources in tests and Storybook is the same seam used in production. No mocks, no vi.mock, no global fetch swap — just a different Layer value in one atom.

The layer is a real implementation with a knob

Korri never ships a Mock source. It ships one real in-memory layer whose behavior you configure. From library-source-layer-memory.ts:

behaviorWhat the source doesUI state it drives
{ kind: "ready" }returns seeded gamesReady
{ kind: "loading-forever" }Effect.neverLoading (the production default seam!)
{ kind: "fail-list", error }Effect.fail(error)LoadError

Same pattern for the launcher: makeInMemoryLauncherLayer({ behavior: { kind: "succeed" | "fail" | "managed" | "defect" } }). "Fakeness" lives in the config, never in the type name.

Two ways to override the seam

1 — Seed at boot with RegistryProvider initialValues

For Storybook stories and React tests, hand the registry a starting value for the layer atom. This is the composition-root move — the story chooses the data strategy: 

// A Storybook decorator / test wrapper — a composition root
function withLibraryLayer(layer) {
  return (Story) => (
    <RegistryProvider
      initialValues={[
        [librarySourceLayerAtom, layer],   // override layer 2
      ]}
    >
      <Story />
    </RegistryProvider>
  )
}

// The "list failed to load" story — no mocks anywhere
export const LoadError = {
  decorators: [
    withLibraryLayer(
      makeFailingLibrarySourceLayer(
        new LibraryError({ reason: "config", message: "boom" }),
      ),
    ),
  ],
}

2 — Set imperatively with registry.set

From plain TS (no JSX) — e.g. a non-React test or a boot script — get the registry and write the atom directly. It's synchronous and returns void: 

registry.set(librarySourceLayerAtom,
  makeInMemoryLibrarySourceLayer({ behavior: { kind: "ready" }, games: seed }))

// from inside an Effect instead:
yield* Atom.set(librarySourceLayerAtom, nextLayer)  // needs AtomRegistry in context
Gotcha worth memorizing: atoms are not singletons — they are inert descriptors. All state lives in the AtomRegistry. The same atom in two registries holds two independent values, so each story/test gets a fresh registry and clean state for free.

Q. A teammate adds vi.mock("../library-services") to make a Storybook story show the error state. What's wrong, and what's the one-line fix?

Reveal answer

It breaks the harness posture — no mocks in stories. The component now depends on a mocking layer that only exists in the story. The fix: delete the mock and override librarySourceLayerAtom via RegistryProvider initialValues with makeFailingLibrarySourceLayer(...). Same seam as production, real implementation, configurable behavior.

Why this matters

Every meaningful UI state — Loading, Ready, Empty, LoadError, Defect, failed-launch — is reachable by setting one atom to a real layer with the right behavior. That's what makes Korri's Storybook honest and its tests deterministic. Master this seam and you can stage any state without touching a component.
