Anatomy of a Korri atom stack

Before you can safely change Korri UI state, you need to read an atom stack and name its parts. This lesson teaches the five layers of library-atoms.ts — then you label the real lines yourself.

~8 minutes   Mission goal: "read a Korri atom stack and identify the parts"

The one win: after this lesson you can point at any line in product/platform/react/library/library-atoms.ts and say which of the five roles it plays. That is the prerequisite for every later lesson where you modify the stack.

The five layers, top to bottom

Every Korri atom feature flows through the same five roles. Data flows down (a service describes a capability; a layer supplies it; a runtime atom holds the layer; a data atom runs an Effect; a hook reads it into React). The seam you swap in tests and Storybook is the layer atom — layer 2.

  • 1Service — the contractA capability declared with Context.Service. It names what can happen (e.g. LibrarySource, Launcher), never how. Programs ask for it with yield* LibrarySource.
  • 2Layer (held in an atom) — the swappable wiringA Layer constructs the service. Korri parks it inside Atom.make(...) so production, tests, and stories can override the implementation at one seam — the ...LayerAtom.
  • 3Runtime atom — the engineAtom.runtime(get => Layer.merge(...)) turns the chosen layers into a runtime that can execute Effects. It reads the layer atoms with get(...), so swapping a layer atom rebuilds the runtime.
  • 4Data / function atom — the workruntime.atom(Effect.gen(...)) produces async Result state for reads; runtime.fn(...) produces a callable command for writes (e.g. launchAtom).
  • 5React hook boundary — the edgeComponents read with useAtomValue(dataAtom) and trigger commands with useAtomSet(fnAtom). This is where Effect meets React — and where raw Result/Exit should be converted into a domain ADT.
Mental model: a data atom is a recipe; the runtime atom is the kitchen; the layer atom decides which ingredients (real or fixture) the kitchen stocks. Components never touch ingredients directly — they order through the hook.

The real code, annotated

This is the actual Korri source (lightly trimmed). Each colored marker is one of the five layers. Read it once, then do the exercise below. 

// [2] LAYER ATOMS — the swappable seam (production default shown)
export const librarySourceLayerAtom = Atom.make(loadingForeverLibrarySourceLayer)
export const launcherLayerAtom     = Atom.make(makeInMemoryLauncherLayer({ behavior: { kind: "succeed" } }))

// [3] RUNTIME ATOM — merges the chosen layers into an executable runtime
export const libraryRuntime = Atom.runtime(get =>
  Layer.merge(get(librarySourceLayerAtom), get(launcherLayerAtom)),
)

// [4] DATA ATOM — runs an Effect that asks for the [1] service
export const libraryItemsAtom = libraryRuntime.atom(
  Effect.gen(function* () {
    const source = yield* LibrarySource   // [1] SERVICE: the contract
    if (source.listPlayableEntries) return yield* source.listPlayableEntries()
    const legacyGames = yield* source.list()
    return legacyGames.map(playableEntryFromResolvedGame)
  }),
)

// [4] FUNCTION ATOM — a command (write), not a read
export const launchAtom = libraryRuntime.fn<LaunchInput | string>()(input =>
  Effect.gen(function* () {
    const source   = yield* LibrarySource
    const launcher = yield* Launcher      // [1] another SERVICE
    const spec     = yield* source.launchSpecFor(/* ... */)
    return yield* launcher.run(spec, { source: /* ... */ })
  }),
)

Notice the hook layer (5) is not in this file — it lives in the components that import these atoms (useAtomValue(libraryItemsAtom), useAtomSet(launchAtom)). That separation is deliberate: the atoms file is transport/runtime; the component file is React.

Q. You want a Storybook story where the library list shows the error state. Which of the five layers do you change, and which do you leave untouched?

Reveal answer

Change layer 2 only — override librarySourceLayerAtom with a failing layer. The runtime atom (3), data atom (4), and hook (5) stay identical, because the runtime reads the layer atom with get(...) and rebuilds itself. The component never knows it got a failing layer — that is the whole point of the seam.

Why this matters

If you cannot name these five roles, every edit feels like guessing. Knowing them tells you where to make a change: new capability → a service; new test/story behavior → a layer atom; new derived read → a data atom; new React surface → a hook + ADT conversion. The roles are the map.
