### 1. Steam ARM64 Self-Update Relaunch Loop on Bandai

- **File**: `docs/solutions/runtime-errors/steam-arm64-stable-self-update-relaunch-loop-2026-06-27.md`
- **Module**: Korri Steam ARM64 runtime (`korri-steam-guest`, `korri-steam-seed.service`)
- **Problem Type**: `runtime_error`
- **Severity**: high
- **Relevance**: Directly describes the update-loop symptom the plan must fix — Steam exits status 42, `Restart=on-failure` re-enters the updater, loop never resolves.

**Key Insight**: The loop is caused by a stale **pending marker** file surviving after a completed update. Removing `package/steam_client_steamdeck_stable_linuxarm64` (the un-suffixed pending marker — distinct from `.installed` and `.manifest`) and letting Steam complete one repair pass breaks the cycle. Critical pre-conditions:

- The ARM64 channel **must** be `steamdeck_stable` (write to `package/beta`). The generic `steam_client_linuxarm64` URL returns 404; `publicbeta` is not required and should not be the default.
- **Never use update-suppressing flags** (`-nobootstrapupdate`, `-skipinitialbootstrap`, `-norepairfiles`) while recovering a drifted mutable tree — they prevent Steam from completing the repair pass it needs to settle.
- `status=42` + `"Update complete, launching Steam"` is Steam's self-relaunch request, **not** a terminal failure. The service must be configured to restart on it (`Restart=on-failure`, `RestartSec=2`).
- Kill all Steam entry points and clear shared-memory handles (`/dev/shm/u*-ValveIPCSharedObj-Steam`) before starting the recovery pass.
- During visibility debugging, **check Sway's tree** (`swaymsg -t get_tree`) before assuming Korri is hiding Steam. Steam may simply not have mapped a client window yet because it is still in the updater phase.

**Recovery sequence** (stop services → clear `/dev/shm` IPC handles → verify `package/beta` = `steamdeck_stable` → remove pending marker → `systemd-run` with `Restart=on-failure` and **no update-suppressing flags**).

### 2. FEX `srt-bwrap` Must Cross the Architecture Boundary Explicitly

- **File**: `docs/solutions/runtime-errors/steam-sniper-fex-bwrap-architecture-path-2026-06-19.md`
- **Module**: Steam plugin / `steam-guest-runtime-prep`
- **Problem Type**: `runtime_error`
- **Severity**: high
- **Relevance**: Directly describes how pressure-vessel/Sniper runtime prep fails on ARM64 and what the generated `srt-bwrap` wrapper must look like.

**Key Insight**: The `srt-bwrap` trampoline generated by `steam-guest-runtime-prep` sits on the ARM64-host / x86-rootfs architecture boundary. Three properties are **all required simultaneously**:

1. `bwrap` must be resolved from the **x86_64 FEX rootfs** (`${FEX_ROOTFS}/usr/bin/bwrap`), not from host PATH.
2. The host tool path (`/run/current-system/sw/bin`) must be **prepended to `PATH`** so bwrap's child sanity commands (e.g. `true`) find a host-executable binary.
3. The x86_64 bwrap must be invoked **explicitly through `/usr/bin/FEX`**, not through binfmt assumptions.

Missing any one of these properties produces an `Exec format error` at a different depth in the call chain. These three properties must be smoke-tested together after every `steam-guest-runtime-prep` run.

Additional traps to avoid:
- **Do not start Steam ad hoc over SSH** as a product proof. The `korri-steam.service` envelope supplies `HOME`, `STEAM_HOME`, `XDG_RUNTIME_DIR`, `FEX_ROOTFS`, `LimitNOFILE`, group access. Direct SSH starts can produce unrelated resource-limit failures (`socket(): Too many open files`, `std::bad_alloc`) that look like Steam bugs.
- `steamid=0` in helper processes does **not** mean Steam cannot launch; watch for `GameAction [AppID N]` and `SteamLaunch AppId=N` in logs.
- **Keep Steam visible during debugging.** The Sway scratchpad policy can hide prompts, making it impossible to tell whether a launch dialog is waiting.

**Proof of full stack**: verified launch chain: `Steam -applaunch → SteamLaunch AppId → SteamLinuxRuntime_sniper/_v2-entry-point → Proton 10/proton → /usr/bin/FEX … wine64-preloader … Game.exe` with visible fullscreen window, Freedreno GPU node, and shader cache entries.

### 3. ARM64-Native `proton-cachyos` Is the Required Compat-Tool Default

- **File**: `docs/solutions/tooling-decisions/arm64-native-proton-cachyos-steam-runtime-bandai-2026-06-20.md`
- **Module**: `product/plugins/steam`
- **Problem Type**: `tooling_decision`
- **Severity**: high
- **Relevance**: The canonical decision on which Proton compat tool to use for x86 Steam games on ARM64 Bandai, including the GL-wall explanation, install mechanics, VDF bypass playbook, and validation methodology.

**Key Insight**: x86 Proton + FEX + Sniper hits an **unsolvable OpenGL wall** on ARM64:
- FEX's GL support is a query/thunk overlay, **not** an on-disk `libGL.so` the game can `dlopen`.
- `sniper`'s pressure-vessel runtime **isolates** the x86 `libGL` namespace from the host thunk, so the overlay never reaches the game.
- No configuration of the x86-Proton-on-FEX stack closes this gap.

**The fix is structural**: default the compat tool to **ARM64-native `proton-cachyos`** (`proton-cachyos-11.0-20260601-slr-arm64`). Only the game's x86 executable is emulated (via wine WoW64 `libwow64fex.dll`); wine, GL, and audio run as native ARM64 against Adreno (Turnip/Mesa). 26 of 29 validated titles render correctly.

**Critical install mechanics**:
- Install into `/var/lib/korri/steam/compatibilitytools.d/`.
- Remove `require_tool_appid` from `toolmanifest.vdf` — otherwise the tool is pinned to the ARM64 sniper AppID `4185400` which isn't a registered tool in the guest, dead-ending the chain.
- Set as global default via `CompatToolMapping "0"` in `config.vdf` (priority 250).
- **Must run inside the Korri Steam FHS bwrap** (`steam-arm64-fhs`) — provides `/usr/bin/python3.13`, consistent glibc, and `/run/opengl-driver` for the native Adreno GL stack.
- The x86 per-game override path (`proton_experimental`) is currently **non-functional** (fails with `AppError_51` — nested pressure-vessel cannot spawn inside the gamescope FHS). Do not treat it as a fallback.

**VDF/first-launch-gate bypass playbook** (all must be done with Steam **stopped**):
- Headless install: write `appmanifest_<id>.acf` with `StateFlags=1026`, start Steam to auto-download.
- EULA bypass: write `<appid>_eula_0 "1"` in the **first** app block of `userdata/<id>/config/localconfig.vdf`.
- Cloud bypass: set `CloudEnabled "0"` in `~/.steam/registry.vdf`.
- Configurator interstitials: append to `Deck_ConfiguratorInterstitialApps_<Type>` arrays.

**Screenshot validation**: use `gamescopectl screenshot <path>` (4-second async delay), **not** `grim -o DSI-2`. After panel DPMS-blanks, `grim` captures pure black even while gamescope is presenting. Identical byte sizes between two `gamescopectl` captures = stale last-presented surface; restart the session.

### 4. Gamescope `--backend auto` Fights Sway for DRM Master (Use `--backend wayland`)

- **File**: `docs/solutions/runtime-errors/gamescope-backend-auto-fights-sway-for-drm-master-2026-05-27.md`
- **Module**: `tools/device/game-stream-fullscreen` + `korri/shared/library/config`
- **Problem Type**: `runtime_error`
- **Severity**: critical
- **Relevance**: Any Gamescope invocation under Sway on SM8550/Sobo must use `--backend wayland`. The `auto` default resolves to `drm` and produces the "I can hear the game but can't see it" symptom.

**Key Insight**: `--backend auto` is correct **only on bare metal** where Gamescope is the sole compositor. Under Sway (kiosk, nested, dev workstation), `auto` resolves to `drm`, which tries to acquire DRM master while Sway already holds it. The result is a tight restart loop (`Could not make device fd drm master: Device or resource busy`) with no visible window but working audio.

**The fix**: `--backend wayland` makes Gamescope a wayland client of the outer compositor. This is now the **cascade default** (`DEFAULT_GAMESCOPE_POLICY.backend = "wayland"`) in the in-tree `composeGamescopeLaunchSpec` path. Standalone-DRM deployments override to `drm` explicitly in their YAML.

**Design lesson**: `exposeWayland` is a **cascade-folded policy field**, not an inferred signal. The old `launchesNativeWaylandChild` heuristic was deleted — explicit policy prevents silent drops during cascade merges. Any new Gamescope invocation must pin `backend` explicitly; relying on `auto` is a latent "I can hear it but not see it" waiting to happen.

**Reviewer rule**: any new invocation of `gamescope …`, `mpv --vo auto`, or similar must pin its backend in policy. `auto` is "I don't care" — a nested compositor makes that catastrophic.

### 5. Steam Inside Gamescope Preserves Steam Input; Per-Game Wrapping Breaks It

- **File**: `docs/solutions/architecture-patterns/steam-inside-gamescope-preserves-steam-input-2026-06-15.md`
- **Module**: Bandai Steam launches
- **Problem Type**: `architecture_pattern`
- **Severity**: high
- **Relevance**: Defines the correct launch topology for Steam/Proton games on Bandai when both Gamescope resolution control and Steam Input are needed.

**Key Insight**: Steam Input is part of the **Steam session architecture**, not just an input device. Putting only the game inside a nested or detached Gamescope instance moves the game across a focus/input boundary that Steam Input does not bridge reliably.

**The rule**: Run **Steam itself inside the Gamescope session**, then let Steam launch the game normally. The working shape:

```sh
SDL_VIDEODRIVER=x11 gamescope --backend sdl \
  -w 854 -h 480 -W 1920 -H 1080 -F fsr --mangoapp \
  -- korri-steam-guest /var/lib/korri/steam/steamrtarm64/steam \
       -gamepadui -steamos3 -steampal -steamdeck \
       -noverifyfiles -nobootstrapupdate -skipinitialbootstrap -norepairfiles
```

Then launch the game through `steam://rungameid/<appid>` — **not** by replacing its command with another Gamescope wrapper.

**What fails**: per-game `gamescope %command%` in Steam LaunchOptions breaks controller input for Steam-Input-sensitive games, even with `SDL_VIDEODRIVER=x11` or `DISPLAY=:1` variants. Verified A/B on Bandai with Stray (AppID 1332010).

**Additional**: for FSR upscaling, internal and output dimensions must differ (`-w 854 -h 480 -W 1920 -H 1080`). `--mangoapp` reports the Gamescope/output side, not the game's inner swapchain.

### 6. Steam ARM64 Manifest Must Exist Before Desktop Launch (Spinner/404 Loop)

- **File**: `docs/solutions/runtime-errors/steam-desktop-ui-arm64-manifest-spinner-rocknix-2026-05-04.md`
- **Module**: ROCKNIX Steam ARM64 desktop UI
- **Problem Type**: `runtime_error`
- **Severity**: medium
- **Relevance**: Describes the ROCKNIX ARM64 Steam bootstrap condition where a missing `.manifest` file causes `steamwebhelper` to start with `buildid=0` and fall into a 404 update loop.

**Key Insight**: Without `package/steam_client_steamdeck_stable_linuxarm64.manifest`, Steam cannot associate the running native ARM64 client with a non-zero installed version. `steamwebhelper` starts as `buildid=0`, abandons `steamdeck_stable`, and tries `steam_client_linuxarm64` (HTTP 404), causing an infinite spinner.

**The fix**: Recreate the manifest **immediately before** each desktop Steam launch, deriving the version from `steam_client_steamdeck_stable_linuxarm64.installed` (not hardcoded):

```sh
STEAM_CLIENT_VERSION=$(awk -F"[,;]" \
  'NR == 1 && $3 ~ /^[0-9]+$/ { print $3; exit }' \
  "$STEAM_ROOT/package/steam_client_steamdeck_stable_linuxarm64.installed")
# Then write manifest with derived version
```

Steam may clear or rewrite package metadata during startup — always derive at launch time. This is a **Korri pre-start responsibility**, not something Steam self-heals.

**Note**: Desktop Steam on ROCKNIX ARM64 is an experimental utility path. The reliable game launch path on ROCKNIX remains Gamescope/GamepadUI via `runemu.sh`. Desktop mode is useful for debugging but not a primary launch surface.

### 7. Steam Input Requires `/dev/uinput` at `root:input 0660` on Bandai

- **File**: `docs/solutions/integration-issues/steam-uinput-permissions-block-virtual-xinput-2026-06-13.md`
- **Module**: `korri-steam` / `product/systems/nixos/modules/korri-steam.nix`
- **Problem Type**: `integration_issue`
- **Severity**: high
- **Relevance**: Any lifecycle fix that involves Steam Input on SM8550 must ensure this permission precondition.

**Key Insight**: Steam Input is a two-part path. Steam seeing the physical controller (InputPlumber / raw-gamepad detection) is **only the first half**. Steam must also open `/dev/uinput` and create a virtual XInput device the game consumes. With `root:root` ownership, the Korri user cannot open `/dev/uinput` and in-game controls silently fail even though Steam's controller config loads correctly.

**The fix** (commit `ad343ec` in `korri-steam.nix`): the Steam uinput prep helper must converge `/dev/uinput` to `root:input 0660` **in both cases** — when the character device already exists and when it must be created from the kernel `major:minor` pair. The `make_accessible` helper (`chgrp input` + `chmod 0660`) must run in both paths.

**Validation checklist** (must be in the lifecycle plan):
1. `nix build .#checks.x86_64-linux.korri-steam-module`
2. `ls -l /dev/uinput` → expect `crw-rw---- root input`
3. Restart Steam so it reopens the node.
4. Launch a controller-bearing game and confirm input reaches in-game (not just that Steam detects the controller).

### 8. Gamescope Is a Plugin, Not a Platform Concept

- **File**: `docs/solutions/architecture-patterns/gamescope-as-plugin-owned-composition-2026-06-17.md`
- **Module**: `product/plugins/gamescope` + launch-composition + nix-composition
- **Problem Type**: `architecture_boundary` (inferred)
- **Relevance**: Any lifecycle work that touches Gamescope wiring in platform/service/Nix module code is subject to this boundary rule.

**Key Insight**: Gamescope is a **first-party Korri plugin** (`@korri:gamescope`), not a built-in platform concept. Generic Korri code — platform, services, apps, themes, reusable Nix modules — **must not name Gamescope**. The correct authored config is `launch.with."@korri:gamescope"`, not a top-level `gamescope` field.

**Allowed naming locations**: `product/plugins/gamescope/**`, explicit product/image composition entrypoints, durable docs.

**Operational consequence**: if the plan adds or modifies Gamescope behavior, those changes must live in the plugin, not in generic services or Nix modules. A "no-Gamescope" composition must still evaluate correctly and keep generic services usable.

### 9. Manual ROCKNIX ARM64 Steam Launch — Full Stack Requirements

- **File**: `docs/solutions/best-practices/manual-steam-game-launching-rocknix-arm64-2026-05-04.md` (last updated 2026-06-13)
- **Module**: ROCKNIX Steam ARM64 manual game launching
- **Problem Type**: `best_practice`
- **Severity**: medium
- **Relevance**: Reference for debugging any Steam/Proton/Gamescope lifecycle issue on SM8550 handhelds; catalogues what fails and why.

**Key Insights** (consolidated):

| What you try | What actually happens |
|---|---|
| Raw SSH `gamescope --backend drm` | Fails: cannot open seat (`No backend was able to open a seat`) |
| Direct Proton without SteamLinuxRuntime | Fails: `wine: could not load ntdll.so` |
| Nested Gamescope without Steam desktop context (cold boot) | Fails: `Primary child shut down!` |
| Nested Gamescope `--backend wayland` (ad-hoc, manual path) | Aborted during input/window setup (different from the verified in-tree cascade path) |
| Nested Gamescope `--backend sdl` without `SDL_VIDEODRIVER` | Audio runs, no visible Sway window |
| Nested Gamescope `--backend sdl SDL_VIDEODRIVER=x11` | **Working**: Sway maps `class=gamescope` window |

**Required stack for manual ARM64 launch**:
- Stop `essway`, keep (or start) `sway` session.
- Start Steam desktop UI in the background first — it initializes session/runtime state the manual command chain relies on.
- Launch graphical commands via `swaymsg exec` or a self-relaunching script, not raw SSH.
- Use `SteamLinuxRuntime_sniper/_v2-entry-point --verb=waitforexitandrun` as the outer wrapper (not bare `proton`).
- Use landscape Gamescope dimensions (`-W 1920 -H 1080`), not portrait DRM dimensions, under Sway.
- Set `PROTON_USE_XALIA=0` — without it, Proton 10 can crash with `System.Exception: x11 not available`.
- Verify game success via `AppID N state changed : Fully Installed,App Running` in `content_log.txt`, not process names (pressure-vessel wrappers can survive after game exit).

**Proton version notes**:
- Proton 10.0: reliable for Balatro.
- Proton 11.0 (beta2): can start the stack but fails to produce a stable game process on this build; hold off until retested with a clean prefix.
- GE-Proton10-34: verified working; warns about prefix version mismatch when reusing a Proton 10/11-touched prefix.
- Check the `version` file inside the compatibility tool directory — symlink directory names can lie (e.g., a `Proton 11.0 (ARM64)` symlink that points to Proton 10.0).
- Use a separate `STEAM_COMPAT_DATA_PATH` per compatibility tool during experimentation to avoid prefix churn.

### 10. FEX / Proton / Steam Plugin Ownership Boundary

- **File**: `docs/solutions/architecture-patterns/fex-substrate-and-steam-runtime-boundary-2026-06-20.md`
- **Module**: `product/plugins`
- **Problem Type**: `architecture` (inferred)
- **Relevance**: Defines which plugin owns which piece of the ARM64 Steam runtime; prevents ownership confusion when implementing the lifecycle fix.

**Key Insight**: Three ownership domains, each with a distinct plugin:

| Plugin | Owns |
|---|---|
| `@korri:fex` | FEX rootfs path, Vulkan ICD contract, generic FEX substrate facts |
| `@korri:proton` | Proton runtime defaults (Proton 10 root, Wine DLL overrides, GL driver path) |
| `@korri:steam` | Steam AppID launch, install authority, service envelope, `steam-guest-runtime-prep`, pressure-vessel repair, `srt-bwrap` handling, visibility policy, AppID cleanup |

**Current deployment caveat**: FEX rootfs and Proton 10 root are physically provisioned at their Steam paths today (`/var/lib/korri/steam/fex-rootfs`, `/var/lib/korri/steam/steamapps/common/Proton 10.0`). The ownership split is **code ownership only** — it does not yet make FEX provisioning Steam-independent.

**Rule**: Do not move `steam-guest-runtime-prep`, pressure-vessel wrapper repair, `srt-bwrap`, Steam AppID launch, or Steam foreground cleanup into `@korri:fex`. Those contracts are consequences of Steam's mutable runtime.

## Recommendations

### For the lifecycle fix plan

1. **Anchor the ARM64 channel first.** Every Steam lifecycle fix starts with `package/beta = steamdeck_stable`. Nothing else should default, and the channel should be written by Korri pre-start, not left for Steam to infer.

2. **Model the update loop correctly.** `status=42` is a relaunch request. The NixOS service must have `Restart=on-failure` and `RestartSec=2`. A one-shot `systemd-run` without restart is structurally wrong — Steam's updater exits 42 to trigger the real client, and the service must follow it.

3. **Separate manifest prep from the Steam client.** The `steam_client_steamdeck_stable_linuxarm64.manifest` file must be written by Korri before each launch, derived from the `.installed` file. Steam may clear it. This is a Korri invariant, not a Steam self-healing behavior.

4. **Implement a recovery helper that clears only the stale pending marker.** Back up `package/`, then remove `package/steam_client_steamdeck_stable_linuxarm64` (un-suffixed — the pending marker). Keep `.installed` and `.manifest`. This is the surgical reset, not a full wipe.

5. **Smoke-test `srt-bwrap` after every `steam-guest-runtime-prep` run.** The test must assert all three properties: FEX rootfs bwrap path, host PATH prefix, explicit `/usr/bin/FEX` invocation. Treat the absence of any one property as a regression.

6. **Default the compat tool to `proton-cachyos` ARM64-native.** The x86 Proton + FEX + Sniper path has an unsolvable GL wall. The global `CompatToolMapping "0"` must point at the ARM64-native build. Per-game overrides go in the same map, not as a stack-level fallback.

7. **Gamescope backend must be explicit.** `--backend wayland` for all kiosk/Sway deployments. This should come from the cascade default, not be specified ad hoc per invocation. Any new gamescope invocation that doesn't set `backend` explicitly is a latent "audio without video" bug.

8. **Fix `/dev/uinput` permissions in the NixOS module.** Ensure `korri-steam.nix`'s prep helper reaches `root:input 0660` on both the pre-existing and freshly-created node paths. Add this to the lifecycle smoke-test gate.

9. **Do not use update-suppressing flags for production launches.** `-nobootstrapupdate`, `-skipinitialbootstrap`, `-norepairfiles` are for desktop-mode manual debugging only. Using them in the product lifecycle prevents Steam from completing the self-repair that breaks the update loop.

10. **Keep Steam visible during any debugging phase.** Remove Sway scratchpad/hide rules for Steam windows and kill the Korri GUI first, then verify `swaymsg -t get_tree` shows a Steam window. If no window appears, Steam is likely still in the updater — check logs before blaming visibility.

11. **Run `korri-steam.service` as the proof envelope.** Ad-hoc SSH Steam starts miss `LimitNOFILE`, `FEX_ROOTFS`, group access, and session bus. They produce false failures that look like Steam bugs. The service is the authoritative proof context.

12. **Keep the architecture boundary clean.** `srt-bwrap`, runtime prep, and pressure-vessel repair stay in `@korri:steam`. FEX rootfs path facts belong in `@korri:fex`. Proton runtime defaults belong in `@korri:proton`. The plan should not collapse these into Steam-owned literals scattered across shell scripts.
