# Research: SteamTinkerLaunch risks for Korri Steam launch modes

## Summary
SteamTinkerLaunch (STL) is maintained and widely used, but it is a very broad Steam wrapper/compatibility-tool system, not a small launch-mode primitive. Korri should borrow only narrow patterns—Steam compatibility-tool packaging, explicit per-AppID logging, and separation of native launch-option vs Proton compatibility-tool paths—while avoiding STL’s brittle areas: Steam client/VDF heuristics, `%command%` parsing, Steam Deck/Game Mode UI behavior, runtime/container assumptions, and on-launch dependency management.

## Findings
1. **STL is maintained, but the project has high bus-factor and scope risk.** The upstream README says SteamTinkerLaunch is a Linux Steam wrapper for configuring many tools—Gamescope, MangoHud, mod managers, custom Proton/Wine, Winetricks, ReShade, SpecialK, etc.—and the wiki/search results state it is “currently maintained by sonic2kk”; release notes say creator frostworx stepped down and sonic2kk took over after a maintenance gap. The local script reports `PROGVERS="v14.0.20250602"`, and GitHub search shows open issues into 2026, so it is not abandoned, but it is a large shell monolith with active churn. [README](https://github.com/sonic2kk/steamtinkerlaunch) [Releases](https://github.com/sonic2kk/steamtinkerlaunch/releases) [Script](https://github.com/sonic2kk/steamtinkerlaunch/blob/master/steamtinkerlaunch)

2. **Steam UI/VDF integration is inherently brittle.** STL’s `compat add` path creates `compatibilitytool.vdf`, `toolmanifest.vdf`, and a symlink under Steam’s `compatibilitytools.d/SteamTinkerLaunch`; an issue reports failures where STL tried to write `/SteamTinkerLaunch/compatibilitytool.vdf` and `/SteamTinkerLaunch/toolmanifest.vdf`, and another notes Steam Cloud behavior depended on the internal compatibility-tool name starting with `Proton`. This means correctness depends on undocumented Steam client expectations, path discovery, write permissions, and VDF string details. [Issue #408](https://github.com/sonic2kk/steamtinkerlaunch/issues/408) [Issue #185](https://github.com/sonic2kk/steamtinkerlaunch/issues/185) [Script](https://github.com/sonic2kk/steamtinkerlaunch/blob/master/steamtinkerlaunch)

3. **`%command%` and launch-option handling is a common failure surface.** STL documents two modes: compatibility tool for Proton games, and `steamtinkerlaunch %command%` as a Steam launch option for native Linux games; it explicitly says launch-option mode for Proton games is not intended/advised. Issues show users struggle to preserve existing launch options like `SteamDeck=0 %command% -FSRFG -DLSSFG`, custom-command arguments, and prepended commands, and STL’s script has logic that detects whether Proton appears in the incoming command and changes behavior based on that. Korri should not emulate shell-string rewriting of arbitrary Steam launch options; it should keep command construction as arrays and treat Steam’s incoming command as opaque except for a minimal, tested wrapper boundary. [Steam Launch Option wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Launch-Option) [Issue #1191](https://github.com/sonic2kk/steamtinkerlaunch/issues/1191) [Issue #530](https://github.com/sonic2kk/steamtinkerlaunch/issues/530) [Script](https://github.com/sonic2kk/steamtinkerlaunch/blob/master/steamtinkerlaunch)

4. **Steam Deck/Game Mode is a separate risk class, not just “Linux Steam”.** STL’s README notes Steam Deck may require an absolute path like `$HOME/stl/prefix/steamtinkerlaunch %command%`; issue #630 reports native games on Steam Deck Game Mode hanging at the loading screen and never showing the Wait Requester, while working in Desktop Mode. Other Deck issues involve menus not showing, Vortex/MO2 launch failures, SD-card compatdata symlink behavior causing prefixes to be read as Proton `None` and overwritten, and dependency downloads. Korri should validate launch wrappers in the actual foreground session/Game Mode analogue, not infer success from Desktop Mode or direct terminal launches. [README](https://github.com/sonic2kk/steamtinkerlaunch) [Issue #630](https://github.com/sonic2kk/steamtinkerlaunch/issues/630) [Issue #692](https://github.com/sonic2kk/steamtinkerlaunch/issues/692) [Issue #877](https://github.com/sonic2kk/steamtinkerlaunch/issues/877)

5. **Steam Linux Runtime/Proton assumptions can break wrappers.** STL wiki/issues document that when SLR starts inside compatibility-tool mode, system-file access can be rejected from the container, making STL and optional third-party tools inaccessible; another issue says after Steam launch-process changes it was no longer possible to fully disable SLR when running as `stl %command%` because SLR is hooked immediately. STL’s own script contains logic to discover Proton, Wine, `require_tool_appid`, and Steam Linux Runtime paths. For Korri, this argues for using the narrowest host-side wrapper possible and explicitly controlling LD_LIBRARY_PATH/runtime closure rather than depending on Steam’s runtime environment. [Steam Linux Runtime wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Linux-Runtime) [Issue #281](https://github.com/sonic2kk/steamtinkerlaunch/issues/281) [Issue #324](https://github.com/sonic2kk/steamtinkerlaunch/issues/324) [Script](https://github.com/sonic2kk/steamtinkerlaunch/blob/master/steamtinkerlaunch)

6. **Dependency sprawl creates launch-time fragility.** STL requires hard dependencies such as `git`, `make`, `gawk`, `xdotool` and Yad, then optionally uses Gamescope, MangoHud, GameMode, Winetricks, innoextract, cabextract, jq, ImageMagick, rsync, 7za, gdb, xdg tools, OBS capture, mod managers, and more. The Steam Deck path downloads Yad AppImages and dependency archives into `$HOME/stl/deps`, supports offline fallback matching, and has issues for failed downloads. This is useful for a tinkering suite, but risky for Korri: launch should not depend on network downloads, GUI toolkit availability, or third-party mod-manager setup. [Installation wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Installation) [Steam Deck wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Deck) [Issue #707](https://github.com/sonic2kk/steamtinkerlaunch/issues/707) [Issue #1149](https://github.com/sonic2kk/steamtinkerlaunch/issues/1149)

7. **STL’s breadth is the reason not to mimic it.** Its value is a universal Swiss-army knife: GUI menus, per-game config, modding, prefix mutation, downloads, custom tools, Steam collections, and compatibility-tool installation. Korri’s goal is narrower: reliable foreground launch under a known Nix/runtime closure. Mimicking STL wholesale would import shell monolith complexity, implicit Steam parsing, mutable per-user state, and third-party tool support burden; the safer path is a purpose-built, AppID-scoped wrapper with deterministic environment setup, explicit logging, no automatic VDF mutation beyond an owned install/reconcile step, and real-device smoke tests. [README](https://github.com/sonic2kk/steamtinkerlaunch) [Script](https://github.com/sonic2kk/steamtinkerlaunch/blob/master/steamtinkerlaunch)

- I did not run STL in Steam/Deck/Game Mode. Next step for Korri is a controlled real-device matrix: native launch option, Proton compatibility-tool style, Game Mode/foreground session, and runtime/container variations.

## Recommendation for Korri
Do not mimic STL as an architecture. Borrow the compatibility-tool packaging idea and per-AppID diagnostics, but keep Korri’s wrapper small, deterministic, host-runtime-aware, and tested against real Steam launches. Avoid dynamic dependency downloads, broad modding/tool orchestration, GUI wait requesters, arbitrary launch-option parsing, and Steam VDF mutation outside a narrow reconcile command.
