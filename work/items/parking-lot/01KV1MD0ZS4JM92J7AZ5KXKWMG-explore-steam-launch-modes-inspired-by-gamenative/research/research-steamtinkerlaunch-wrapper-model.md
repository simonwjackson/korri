# Research: SteamTinkerLaunch wrapper model

## Summary
SteamTinkerLaunch (STL) is primarily a Steam-owned launch wrapper: for native games it is invoked from Steam Launch Options as `steamtinkerlaunch %command%`, while for Proton games its preferred path is registering as a Steam Compatibility Tool named `Proton-stl`. Its useful pattern for Korri is not the large feature surface, but the small wrapper contract: capture Steam's expanded command/environment, classify the launch, prepend/replace host tooling such as Gamescope/MangoHud/Steam Linux Runtime, then exec/wait and log per AppID.

## Findings
1. **STL has two Steam entry modes, and explicitly warns they are different.** For Proton games, the README says the intended path is forcing SteamTinkerLaunch as a Steam Compatibility Tool; for native Linux games, the intended path is a Steam Launch Option: `steamtinkerlaunch %command%`. It also says only one of these options should be used per game, and that Launch Option use for Proton games is possible but not intended. [README](https://github.com/sonic2kk/steamtinkerlaunch#how-do-i-use-it) / [`/tmp/steamtinkerlaunch/README.md`](/tmp/steamtinkerlaunch/README.md)

2. **The `%command%` model is a normal argv wrapper around Steam's fully expanded game command.** STL's main function calls `initAID "$@"`, records the current command line, and treats arguments containing Steam install paths (`steamapps/common`) as a game launch; those paths lead into `setGameVars` and `prepareLaunch`. Later, `launchSteamGame` starts from `INGCMD`/`ORGGCMD`, builds `FINALSTARTCMD`, logs both original and outgoing commands, then calls `startGame`. [`/tmp/steamtinkerlaunch/steamtinkerlaunch` functions `main`, `launchSteamGame`](/tmp/steamtinkerlaunch/steamtinkerlaunch)

3. **Compatibility Tool install is just Steam VDF plus a symlink.** `CompatTool add` creates `$STEAMCOMPATOOLS/SteamTinkerLaunch`, writes `compatibilitytool.vdf` with internal name `Proton-stl`, writes `toolmanifest.vdf` with `"commandline" "/steamtinkerlaunch run"` and `"commandline_waitforexitandrun" "/steamtinkerlaunch waitforexitandrun"`, then symlinks the real script into that directory. The official wiki search result confirms these files are what Steam needs to execute STL as a compatibility tool. [`/tmp/steamtinkerlaunch/steamtinkerlaunch` function `CompatTool`](/tmp/steamtinkerlaunch/steamtinkerlaunch), [Steam Compatibility Tool wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Compatibility-Tool)

4. **Per-game state is keyed by Steam AppID and Steam metadata.** STL initializes AppID early, stores game config under `~/.config/steamtinkerlaunch/gamecfgs`, logs under `~/.config/steamtinkerlaunch/logs`, and creates AppID/title symlinks for logs. It also uses Steam library manifests, compatdata paths, `SteamAppId`, `SteamGameId`, and `SteamOverlayGameId`; `haveNonSteamGame` detects non-Steam games by comparing `SteamAppId` and `SteamOverlayGameId`. [`/tmp/steamtinkerlaunch/steamtinkerlaunch` top-level config variables and `haveNonSteamGame`](/tmp/steamtinkerlaunch/steamtinkerlaunch)

5. **STL assumes Steam is the launcher for robust behavior.** The README says STL supports non-Steam games only so long as they are launched through the Steam client. The code shells back to Steam for capabilities such as `steam://install/<appid>` when fetching Steam Linux Runtime, parses Steam VDF files (`config.vdf`, `localconfig.vdf`, `shortcuts.vdf`), discovers `compatibilitytools.d`, and reasons about Steam's reaper, overlay, and compatibility-tool environment. [README](https://github.com/sonic2kk/steamtinkerlaunch#general-usage), [`/tmp/steamtinkerlaunch/steamtinkerlaunch` functions `commandlineFetchGameSLR`, `addNonSteamGame`, VDF helpers](/tmp/steamtinkerlaunch/steamtinkerlaunch)

6. **The wrapper composes launch tools by constructing an ordered argv, not by mutating Steam globally.** `setSLRReap` resolves Steam Linux Runtime from incoming command, `toolmanifest.vdf` `require_tool_appid`, or known native SLR AppID; `setLinuxCmd`, `setWineCmd`, and `setProtonCmd` prepare game-family-specific commands; `buildCustomCmdLaunch`/`launchSteamGame` then prepend Gamescope, GameMode, custom command, SLR/reaper, Proton/native command, and game args into `FINALSTARTCMD`. [`/tmp/steamtinkerlaunch/steamtinkerlaunch` functions `setSLRReap`, `setLinuxCmd`, `setWineCmd`, `setProtonCmd`, `launchSteamGame`](/tmp/steamtinkerlaunch/steamtinkerlaunch)

7. **Steam Deck support is still Steam-specific, not a generic handheld launcher model.** On Steam Deck, STL installs under `/home/deck/stl`, detects Game Mode by looking for Gamescope `generate-drm-mode`, installs dependencies, and registers itself as a compat tool. It deliberately avoids doing install/update work when it detects it is being invoked by Steam for an actual game. [`/tmp/steamtinkerlaunch/steamtinkerlaunch` functions `steamdedeckt`, `installFilesSteamDeck`](/tmp/steamtinkerlaunch/steamtinkerlaunch)

## Practical recommendations for Korri
1. **Adopt the narrow `%command%` wrapper contract, not STL's full manager.** Korri's Steam wrapper should continue to accept Steam-expanded argv, preserve/log original args and environment, derive AppID explicitly, construct a final argv, and exec/wait. Avoid copying STL's UI/config/download/mod-manager surface.
2. **Keep Steam assumptions explicit.** If a path depends on `SteamAppId`, `SteamOverlayGameId`, Steam library manifests, `compatdata`, or `compatibilitytools.d`, label it as a Steam adapter path. Do not make it the generic Korri launch contract.
3. **Prefer Launch Options for Korri's current Gamescope host wrapper.** Korri's existing model resembles STL's native-game Launch Option path: a host-side wrapper prepends Gamescope/MangoHud and then runs `%command%`. Compatibility Tool registration is useful later only if Korri needs Proton selection/prefix control.
4. **Model per-AppID policy as data.** STL's practical win is per-game config keyed by AppID plus logs keyed by AppID/title. Korri should keep AppID-specific launch policy/log paths centralized, with environment overrides for resolution, Gamescope flags, and diagnostics.
5. **Do not depend on Steam to install missing runtime pieces unless the feature is Steam-only.** STL can call `steam://install/<appid>` for Steam Linux Runtime because Steam is its owner. Korri should prefer Nix/host closures for required tools; use Steam protocol calls only in an explicitly Steam-scoped reconciliation command.
