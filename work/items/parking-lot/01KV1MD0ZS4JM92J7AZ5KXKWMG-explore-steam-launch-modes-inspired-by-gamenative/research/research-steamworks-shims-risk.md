# Research: Steamworks API shims/emulators for Steam games without the Steam client

## Summary
Steamworks shims range from compatibility bridges used by Valve Proton to third-party Steam API emulators and DRM-removal tools. Korri core should avoid shipping, downloading, recommending, or auto-configuring emulators/DRM bypass tooling; the safe product seam is a generic, user-owned launch wrapper/command facility with clear warnings and detection that recommends the real Steam client when Steamworks ownership, DRM, online services, anti-cheat, or account identity are required.

## Findings
1. **Goldberg Emulator and forks emulate Steamworks interfaces, not just process launch.** Goldberg describes itself as a Steam emulator for GNU/Linux and Windows that emulates Steam online features and enables LAN play for games using Steam multiplayer APIs without Steam or internet; `gbe_fork` is an active fork of that project. This is relevant as prior art for the API surface games may probe, but it is not appropriate to embed in Korri because it can substitute for Steam client services and may be used outside legitimate ownership/developer contexts. [Goldberg](https://gitlab.com/Mr_Goldberg/goldberg_emulator), [gbe_fork](https://github.com/Detanup01/gbe_fork)
2. **SmartSteamEmu is a higher-risk, closed/opaque launcher-style emulator ecosystem.** Public mirrors describe extracting emulator files, editing `SmartSteamEmu.ini`, and launching through `SmartSteamLauncher.exe`; release notes also warn unsupported Steam interfaces may crash games. Treat this as a red flag category: provenance is fragmented, binaries are commonly redistributed by third parties, and Korri should not integrate with or document per-tool setup. [SmartSteamEmu mirror](https://github.com/MrKristofere/SmartSteamEmu)
3. **Steamless is explicitly DRM-removal tooling, not a compatibility shim.** Its README/search metadata says it is a “DRM remover of the SteamStub variants” intended to unpack Steam DRM-protected files. Korri core should not call, bundle, detect-and-suggest, or provide workflow affordances for Steamless-style executable modification. [Steamless](https://github.com/atom0s/Steamless)
4. **Valve’s legitimate compatibility path is Proton + the real Steam client.** Proton is Valve’s Steam Play compatibility tool and includes `lsteamclient`, a Wine-side bridge for Steamworks interfaces. That makes `lsteamclient` useful for understanding why Windows Steam games can call Steamworks under Linux, but it is not a standalone entitlement emulator: it depends on Steam’s runtime/client context. [Proton](https://github.com/ValveSoftware/Proton), [lsteamclient](https://github.com/ValveSoftware/Proton/tree/proton_3.7/lsteamclient)
5. **Official Steamworks behavior expects Steam to own launch and API initialization.** Valve documents `SteamAPI_RestartAppIfNecessary` as checking whether the executable was launched through Steam and relaunching it through Steam if not. Steam’s DRM wrapper is documented as verifying ownership and ensuring Steamworks features work by launching Steam before the game. These are strong signals that a title needs the real client rather than a generic direct launcher. [Steamworks API](https://partner.steamgames.com/doc/sdk/api), [Steam DRM](https://partner.steamgames.com/doc/features/drm)
6. **Legal/ToS risk is material.** The Steam Subscriber Agreement restricts copying, modifying, reverse engineering, deriving source from, or removing proprietary notices from Steam content/services/software without Valve’s written consent. Jurisdiction-specific exceptions may exist, but Korri should not design core features around bypassing platform access controls or substituting proprietary services. [Steam Subscriber Agreement](https://store.steampowered.com/subscriber_agreement/)
7. **Security and account risks rise sharply for online/anti-cheat titles.** VAC is a Steamworks/Steam-client component, and Valve states users connecting to VAC-secured servers with identifiable cheats installed can be banned from that game’s VAC-secured servers. Any shim, injected DLL, modified executable, or opaque launcher should be considered incompatible with VAC/anti-cheat contexts unless the game developer explicitly supports it. [Steamworks anti-cheat](https://partner.steamgames.com/doc/features/anticheat), [VAC integration](https://partner.steamgames.com/doc/features/anticheat/vac_integration)
8. **Legitimate use cases exist, but they are narrow and should remain user/developer-owned.** Plausible legitimate cases include a developer testing their own Steamworks integration, offline/LAN preservation for legitimately owned DRM-free or Steamworks-light builds, or compatibility experiments in isolated environments. Valve’s documented developer path uses Steamworks testing packages/App IDs and Steam-managed launch rather than third-party emulators. [Testing on Steam](https://partner.steamgames.com/doc/store/testing)
9. **Detection signals that a game likely needs real Steam:** Steam DRM wrapper/SteamStub presence; runtime errors like “SteamAPI_Init failed”; calls/imports to `steam_api.dll`, `steam_api64.dll`, `steamclient.dll`, or Steamworks.NET/Facepunch wrappers; use of `SteamAPI_RestartAppIfNecessary`; required AppID/ownership checks; use of Steam authentication tickets, lobby/networking, achievements/stats, DLC, cloud saves, overlay, Workshop/UGC, Steam Input, Remote Play, VAC, or third-party anti-cheat. The stronger the account/network/anti-cheat dependency, the more Korri should prefer “launch through Steam” or mark unsupported outside Steam. [Steamworks API](https://partner.steamgames.com/doc/sdk/api), [Steam DRM](https://partner.steamgames.com/doc/features/drm)

## Korri posture
- **Avoid in Korri core:** bundling or downloading Steam emulators; shipping emulator config generators; patching/replacing `steam_api*.dll`; invoking Steamless or any SteamStub unpacker; bypassing ownership/DRM checks; using opaque third-party launcher binaries; providing game-specific instructions that facilitate circumvention; auto-enabling shims for catalog entries.
- **Allow only as user-provided/opt-in:** a generic per-title launch command/wrapper field; user-provided environment variables/files mounted into an isolated prefix; explicit “I own this and accept risk” warnings; offline-only profiles; no Korri-hosted binaries; no automatic download URLs; no anti-cheat/online enablement; clear telemetry/log redaction so user paths/configs are not leaked.
- **Prefer/recommend real Steam when detected:** Steam DRM wrapper, `SteamAPI_Init` failure, `RestartAppIfNecessary` relaunch behavior, Steam account/session dependencies, Workshop/UGC/cloud/DLC/achievements/stats requirements, multiplayer matchmaking/lobbies, VAC/EAC/BattlEye or server-authenticated play.
- **Product framing:** Korri can support “Steam launch modes” as legitimate orchestration: launch installed games through Steam, Gamescope/Proton wrappers, and user-authored commands. It should not become a Steamworks emulator manager.

## Gaps
- No legal conclusion is possible from technical research; have counsel review any shipped UX around user-provided shims or DRM-adjacent wording.
- Game-specific behavior varies widely; validate detection through local logs and launch outcomes per AppID.
- Proton `lsteamclient` internals are large and versioned; a deeper source audit would be needed only if Korri starts detecting Steamworks interface versions or interpreting Proton logs.
