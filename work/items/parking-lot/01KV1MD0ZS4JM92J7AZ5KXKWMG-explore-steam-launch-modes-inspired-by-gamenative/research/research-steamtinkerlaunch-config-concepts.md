# Research: SteamTinkerLaunch config concepts Korri can reuse

## Summary
SteamTinkerLaunch (STL) is valuable less as a feature checklist and more as a product pattern: it turns per-game launch quirks into named, discoverable configuration owned by the launcher instead of hidden Steam launch-option strings. Korri should reuse the concepts of per-game profiles, explicit runtime/tool toggles, conflict-aware launch composition, and user-manageable quirk presets, while avoiding STL's very broad shell-script surface and dozens of tool-specific menus.

## Findings
1. **STL stores launch behavior as layered global/per-game config, with AppID as the stable key.** The README says first launch creates a config tree, usually `~/.config/steamtinkerlaunch`, and that global and per-game files can be edited via GUI or text editor. The local script defines XDG-aware config/data/cache roots and per-game directories such as `gamecfgs/id`, `gamecfgs/title`, `customvars`, `collections`, `regs`, `downloads`, and typed log directories. The wiki search result confirms game-specific config lives under `gamecfgs/id` using the Steam AppID as filename. Korri concept: use a small `LaunchProfile` keyed by source/app id plus optional title alias, with typed sections for runtime, display wrapper, overlays, commands, and diagnostics rather than raw launch strings. [README](https://github.com/sonic2kk/steamtinkerlaunch#configuration), [/tmp/steamtinkerlaunch/steamtinkerlaunch](/tmp/steamtinkerlaunch/steamtinkerlaunch), [Configuration Files wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Configuration-Files)

2. **STL separates Proton compatibility-tool use from native launch-option use.** Its README and wiki distinguish two entry modes: Proton games should use STL as a Steam compatibility tool, while native Linux games should use `steamtinkerlaunch %command%` as a Steam launch option; the wiki notes launch-option use for Proton games is not advised/supported. Korri concept: model launch mode as a first-class enum (`NativeCommand`, `SteamLaunchOptionWrapper`, `CompatibilityToolWrapper`, etc.) with validation, instead of one generic command template. [README](https://github.com/sonic2kk/steamtinkerlaunch#how-do-i-use-it), [Steam Compatibility Tool wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Compatibility-Tool), [Steam Launch Option wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Launch-Option)

3. **Custom Proton selection is a managed runtime choice, not just an environment variable.** STL exposes Proton version switching from its Game Menu, can list official/custom Proton builds, and can download custom Proton releases via commands like `steamtinkerlaunch dlcustomproton|dcp <url|latest|latestge|latesttkg>`. Korri concept: a runtime selector should know where a runtime came from, whether Korri manages it, and whether a profile pins it; downloading/updating should remain a separate acquisition flow, not be entangled with every launch. [Download Custom Proton wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Download-Custom-Proton), [Standalone Proton wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Standalone-Proton), [Proton wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Proton)

4. **Tool integrations are toggleable capabilities with compatibility/conflict rules.** STL advertises GameScope, MangoHud, ReShade, vkBasalt, OBS capture, Replay Sorcery, GameMode, SpecialK, Winetricks, and mod managers. Its wiki snippets show concrete guardrails: MangoApp toggling automatically enables GameScope and disables MangoHud; Steam Deck Game Mode disables STL GameScope/MangoHud to avoid conflicts with SteamOS overlays; ReShade is Proton/Wine-only and native/Vulkan alternatives should use vkBasalt. Korri concept: represent integrations as typed capabilities with prerequisites, conflicts, and generated launch fragments, e.g. `gamescope` owns `mangoapp`, `mangohud` cannot wrap host-side gamescope, and `reshade` is only valid for Wine/Proton profiles. [README feature list](https://github.com/sonic2kk/steamtinkerlaunch#what-does-it-do), [GameScope wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/GameScope), [MangoHud wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/MangoHud), [MangoApp wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/MangoApp), [ReShade wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/ReShade), [Steam Deck wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Deck)

5. **External tools are useful, but STL's breadth should be collapsed into a few Korri product abstractions.** STL's local script declares many optional programs (`gamescope`, `gamemoderun`, `replay-sorcery`, `obs-gamecapture`, `winetricks`, `innoextract`, `7za`, `xdg-open`, debuggers, mod-manager installers), and the README describes custom executables that can run before, after, instead of, or alongside the game. Korri concept: expose a narrow `AuxiliaryCommand` model with timing (`before`, `replace`, `after`, `sidecar`) and lifecycle policy, then ship curated presets for common cases rather than one UI surface per external tool. [README custom executable feature](https://github.com/sonic2kk/steamtinkerlaunch#what-does-it-do), [Custom Command wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Custom-Command), [/tmp/steamtinkerlaunch/steamtinkerlaunch](/tmp/steamtinkerlaunch/steamtinkerlaunch)

6. **Users manage quirks through menus, text config, Steam Collections, and logs.** STL has a short wait requester before launch, a Main Menu for per-game changes, optional text-file editing, Steam Collections that activate features by adding a game to a named collection, and per-AppID/title logs with symlinks for easier identification. Korri concept: support user-visible profile edits and preset assignment, but make presets explicit Korri data (`Balanced`, `SteamOverlaySafeGamescope`, `ProtonGEWithReShade`, etc.) rather than relying on Steam collection names as implicit configuration triggers. Keep per-profile diagnostics and a “why this launch command was generated” view. [README game-specific use and logs](https://github.com/sonic2kk/steamtinkerlaunch#game-specific-use), [README troubleshooting/logs](https://github.com/sonic2kk/steamtinkerlaunch#troubleshooting), [Steam Collections wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Steam-Collections), [Configuration Files wiki](https://github.com/sonic2kk/steamtinkerlaunch/wiki/Configuration-Files)

## Korri product concepts to reuse
- **Launch profile**: stable per-game record keyed by source/app id; contains runtime, wrapper, overlays, auxiliary commands, env, and diagnostics settings.
- **Launch mode**: explicit mode with validation for native, Proton/compat-tool, Steam launch-option wrapper, and future standalone runners.
- **Capability graph**: each integration declares prerequisites, conflicts, generated args/env, and unsupported contexts.
- **Curated presets**: small named bundles that set multiple capability knobs and document intent; users can fork/override per game.
- **Quirk ledger**: user-visible notes and generated-command explanation for each profile, plus per-profile logs.

## What Korri should avoid copying
- A single giant wrapper script as the source of truth for UI, downloads, config mutation, process launch, and tool-specific heuristics.
- Making Steam Collections or magic folder names the primary configuration API.
- Exposing every third-party tool option equally; Korri should prefer a small number of typed launch intents and advanced escape hatches.
- Mixing acquisition, installation, compatibility decisions, and launch-time process composition into one menu flow.
