# Research: SteamTinkerLaunch launch flow internals

## Summary
SteamTinkerLaunch is a single Bash control plane that treats a Steam launch as a recoverable command graph: identify AppID, classify the incoming command, materialize/load config, rewrite Proton/Wine/SLR/reaper/custom-tool command segments, then run and supervise the final command with per-AppID logs. For Korri, the important lesson is not to clone STL's breadth, but to make LaunchSpec capture the same stable seams: launch source, AppID/probe identity, original argv/env, resolved runtime, command segments, config provenance, log targets, and failure reason.

## Findings
1. **Entry dispatch is driven by Steam environment plus command-shape heuristics.** `main` initializes shm/logs, calls `initAID "$@"`, `setAIDCfgs`, language/config setup, dependency/proton initialization, then classifies the invocation: internal commands go to `commandline`, Steam-looking commands containing `steamapps/common` or `link2ea` go through `setGameVars` + `prepareLaunch`, and unknown non-command game paths can use `setCustomGameVars` + `prepareLaunch`. It also special-cases `SteamAppId=0` and suppresses false game detection for known STL commands. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:26883-27218`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

2. **AppID detection is layered, with Steam env first and fallback IDs for standalone/custom launches.** `initAID` prefers `STEAM_COMPAT_APP_ID`, then `SteamAppId`; if `SteamAppId=0`, it derives from `STEAM_COMPAT_DATA_PATH`; for `play` mode it uses an explicit numeric ID or generates an ID from the executable name; otherwise it falls back to `PLACEHOLDERAID`. It also snapshots `STEAM_COMPAT_DATA_PATH` as `OSCDP`. `haveNonSteamGame` identifies Non-Steam games by comparing `SteamAppId` and `SteamOverlayGameId`. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:426-484`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch), [`/tmp/steamtinkerlaunch/steamtinkerlaunch:27057-27078`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

3. **Per-AppID paths are established early and reused everywhere.** `setAIDCfgs` maps an AppID to `STLGAMECFG`, tweak configs, `LOGFILE`, and per-game custom vars; `prepareLaunch` then `linkLog`s, creates project dirs, saves/loads global config, creates/loads the game config, loads custom/generic metadata, runs auto-bump/config transforms, and reloads config after menus. This is effectively config provenance: global defaults -> default template -> per-game config -> metadata/custom vars -> collection/tweak/menu overrides. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:487-507`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch), [`/tmp/steamtinkerlaunch/steamtinkerlaunch:19134-19420`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

4. **Game command parsing decomposes Steam's argv into named command segments.** `setGameVars` detects OS/runtime (`getGameOS`), derives executable path/name, prefix path, install dir, Steam library/appmanifest, and flags for `STEAM_COMPAT_TOOL_PATHS`, reaper, Steam Linux Runtime, Proton in the incoming command, and STL itself. It then slices the raw argv into `INGCMD`, `REAPCMD`, `RUNSLR`, `INPROTCMD`, `INSTLCMD`, compatibility-tool SLR (`RUNSLRCT`), base game command (`ORGGCMD`), and game args (`ORGCMDARGS`). [`/tmp/steamtinkerlaunch/steamtinkerlaunch:2280-2573`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

5. **Windows/native classification is heuristic but explicit.** `getGameOS` uses `STEAM_COMPAT_DATA_PATH` as a strong Windows signal, but if it can find the executable under `STEAM_COMPAT_INSTALL_PATH`, it inspects `file` output: shell/ELF means native Linux (`ISGAME=3`), PE32 means Windows (`ISGAME=2`), and ambiguous cases default to Windows. Non-Steam/custom game paths use `setCustomGameVars`, which still fills `ORGGCMD` and enables SLR lookup for custom programs. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:2574-2635`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch), [`/tmp/steamtinkerlaunch/steamtinkerlaunch:2637-2661`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

6. **Proton selection distinguishes Launch Options mode from Compatibility Tool mode.** `checkStartMode` loads the game config and, for Windows games, if Proton is already present in the Steam-provided command (`HAVEINPROTON=1`, i.e. `steamtinkerlaunch %command%`) it preserves that Proton and disables override. If Proton is absent, it assumes STL is being used as a Steam Compatibility Tool and resolves `RUNPROTON` from configured `USEPROTON`. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:22489-22528`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

7. **Final Proton/Wine/native command construction is segment-based.** `launchSteamGame` refreshes SLR/reaper, builds `GAMEARGSARR` and `GAMESTARTCMD`, dispatches to native adapters (`setLinuxCmd`, Boxtron/Roberta/Luxtorpeda), Wine (`setWineCmd`), or Proton (`setProtonCmd`), then concatenates `FINALSTARTCMD` in order: custom-command prefix, SLR/reaper, external adapter or Proton command, game command, game args. It writes a detailed STARTDEBUG file containing all intermediate segments before calling `startGame`. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:22056-22304`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

8. **`setProtonCmd` is the core Proton resolver.** It preserves incoming Proton when `HAVEINPROTON=1`; otherwise it calls `setRunProtonFromUseProton`, may delete/rebuild prefixes, fixes Proton symlinks, resolves version mismatches, strips initial `waitforexitandrun` from the game command, and prepends `RUNPROTON waitforexitandrun`. Missing Proton is usually logged as WARN/ERROR and may continue to crash unless no fallback exists. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:21895-22055`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

9. **Wine mode bypasses final Steam-style command assembly.** `setWineCmd` resolves a configured Wine build, constructs `RUNWINE`, `RUNWINECFG`, `RUNREGEDIT`, `RUNWICO`, chooses `win32/win64` from executable arch, builds `FINGAMECMD` by stripping `waitforexitandrun`, launches through `extWine64Run`, optionally prefixes gamemoderun/gamescope, logs to `$WINE_LOG_DIR/$AID.log`, and waits for the Wine PID. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:21348-21474`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

10. **Runtime execution supervises logs and process lifetime.** `startGame` creates pid locks, starts helpers, optionally wraps the command in `unshare` for network blocking, applies MO2 rewrites, rebuilds `STEAM_COMPAT_TOOL_PATHS`, logs the full command, restores original env, runs the command through Conty, MangoApp/Gamescope, EA special handling, or direct `"${RUNCMD[@]}" 2>&1 | tee "$GRUNLOG"`, symlinks AppID logs to title logs, waits for detected wine/server/custom pids, records playtime, and resumes steamwebhelper. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:20158-20559`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

11. **Error handling is mostly log-and-continue, with hard exits only for unrecoverable setup.** Dependency checks can `exit` when required internal dependencies are missing; invalid Wine/Proton downloads may call `closeSTL` and `exit`; unsupported adapters log `ERROR` and exit. Many runtime failures only downgrade features (`USEMANGOAPP=0`, skip missing SLR, warn on unknown executable OS, keep running with likely-bad Proton). Cleanup is centralized in `closeSTL`, which touches a close sentinel, restores state, kills helper processes, backs up Steam user data, creates Proton log symlinks, and logs session completion. [`/tmp/steamtinkerlaunch/steamtinkerlaunch:18700-18720`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch), [`/tmp/steamtinkerlaunch/steamtinkerlaunch:25343-25460`](file:///tmp/steamtinkerlaunch/steamtinkerlaunch)

## Implications for Korri LaunchSpec/direct-probe design
- Model launch as **structured segments**, not one string: `originalArgv`, `reaper`, `steamLinuxRuntime`, `compatToolRuntime`, `proton`, `adapter`, `gameExecutable`, `gameArgs`, `wrappers`.
- Preserve **source mode** explicitly: `steamLaunchOptions`, `steamCompatibilityTool`, `nonSteamShortcut`, `directProbe`, `standalone`.
- Capture **identity separately from executable**: Steam AppID, Non-Steam overlay ID, generated probe ID, compat-data path, install path, title, executable basename.
- Make config provenance first-class: global defaults, template defaults, per-AppID settings, collection/profile overrides, runtime-probe overrides.
- Prefer Korri-typed failures over STL's log-and-continue: `MissingRuntime`, `AmbiguousExecutable`, `MissingCompatData`, `UnsupportedLaunchShape`, `ProbeTimedOut`, `ProcessPidUnknown`.
- Direct probes should emit the same LaunchSpec fields as Steam launches; only the source adapter should differ.
