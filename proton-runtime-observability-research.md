# Research: Proton runtime observability surfaces

## Summary
Use process supervision as the canonical source for `launch_requested`, `process_started`, and `process_exited`, then enrich it with opt-in logs from Proton, Steam Linux Runtime/pressure-vessel, DXVK/VKD3D, Gamescope, MangoHud, and FEX. The safest structured lifecycle events come from wrapper-controlled timestamps/PIDs/exit status, Gamescope `--ready-fd`, DXVK/VKD3D log-file presence/content, MangoHud CSV/log output, and Steam Runtime diagnostics; high-volume Wine/pressure-vessel/FEX debug logs should be sampled or enabled only for diagnostic sessions.

## Findings
1. **Runtime preparation is best observed at the Steam Linux Runtime / pressure-vessel boundary.** Valve's runtime bug-reporting docs explicitly name `STEAM_LINUX_RUNTIME_VERBOSE=1`, `PRESSURE_VESSEL_VERBOSE=1`, `CAPSULE_DEBUG=all`, and `G_MESSAGES_DEBUG=all` as additional debug logging knobs, and the diagnostics tool writes `steam-runtime-system-info-*.txt` under `~/.steam/root/logs`. Use these for `runtime_prepare_started`, `runtime_container_ready`, and `runtime_prepare_failed` enrichment, but do not leave full verbosity on by default. [Valve steam-runtime bug reporting](https://github.com/ValveSoftware/steam-runtime/blob/master/doc/reporting-steamlinuxruntime-bugs.md)
2. **Steam Linux Runtime also has lighter launcher-level log toggles.** Valve's pressure-vessel docs and multi-GPU testing instructions reference `STEAM_LINUX_RUNTIME_LOG=1` and `STEAM_LINUX_RUNTIME_VERBOSE=1`; `pressure-vessel-wrap` also documents debug/developer options. These are good opt-in switches when testing GPU/device selection or container setup failures. [pressure-vessel multi-GPU testing](https://gitlab.steamos.cloud/steamrt/steam-runtime-tools/-/blob/main/pressure-vessel/testing-multi-gpu.md), [pressure-vessel wrap manpage](https://gitlab.steamos.cloud/steamrt/steam-runtime-tools/-/blob/main/pressure-vessel/wrap.1.md)
3. **Proton's official log switch is simple and safe when directed to a controlled directory.** `PROTON_LOG=1` dumps a debug log to `$PROTON_LOG_DIR/steam-$APPID.log`; older/common guidance notes `$HOME/steam-$APPID.log` and setting `WINEDEBUG` in `user_settings.py` for deeper logs. Emit a `proton_log_created` event when the file appears and attach path/appid/size/mtime, but use process exit status—not log parsing—as the primary `game_exited` signal. [Valve Proton README](https://github.com/ValveSoftware/Proton), [Proton changelog wiki](https://github.com/ValveSoftware/Proton/wiki/Changelog)
4. **Wine debug logging is powerful but too noisy for always-on lifecycle detection.** Wine documents `WINEDEBUG` as a comma-separated channel/class selector. It can help diagnose exceptions or loader failures, but for structured lifecycle events prefer wrapper PID/exit-code plus optional targeted `WINEDEBUG` capture during repro sessions. [WineHQ environment variables](https://www.winehq.org/docs/wineusr-guid%3Cbr%20/%3Ee/x275)
5. **DXVK exposes machine-usable backend evidence.** The DXVK README documents `DXVK_LOG_PATH`; when set, standalone logs are written in that directory as files such as `app_d3d11.log` and `app_dxgi.log`. `DXVK_HUD=devinfo,...` can display GPU/driver info, but log files are safer for structured `graphics_backend_detected` events: watch for `*_d3d9.log`, `*_d3d11.log`, `*_dxgi.log`, parse adapter/driver/API lines conservatively, and keep the raw file path for audit. [DXVK README](https://github.com/doitsujin/dxvk), [DXVK HUD docs](https://github.com/doitsujin/dxvk/blob/master/README.md)
6. **VKD3D-Proton has explicit log-file and device-selection environment variables.** Its README documents `VKD3D_LOG_FILE` for redirecting `VKD3D_DEBUG` output, plus `VKD3D_VULKAN_DEVICE` and `VKD3D_FILTER_DEVICE_NAME` for Vulkan device selection/filtering. These are suitable for D3D12 `graphics_backend_detected`/`gpu_device_selected` events when enabled per launch. [vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton)
7. **Vulkan loader logs can corroborate ICD/driver selection.** Khronos documents loader filtering/debug env vars such as `VK_LOADER_DRIVERS_SELECT`/`VK_LOADER_DRIVERS_DISABLE`; when logging is enabled, ignored/selected driver messages are emitted. Use this only as diagnostic enrichment because it is lower-level than DXVK/VKD3D and may expose host driver paths. [Khronos Vulkan Loader debugging](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDebugging.md)
8. **Gamescope provides the cleanest compositor/window-readiness signal.** The Gamescope help text in `main.cpp` documents `-R, --ready-fd` as "notify FD when ready" and `--xwayland-count` for creating Xwayland servers. Use `--ready-fd` for `compositor_ready`; then, if the game is Xwayland, observe X11 window creation/mapping on that display with `xwininfo`/`xprop` as a best-effort `window_ready` signal. [Gamescope main.cpp](https://github.com/ValveSoftware/gamescope/blob/master/src/main.cpp), [X.Org xwininfo manpage](https://www.x.org/archive/X11R7.7/doc/man/man1/xwininfo.1.xhtml)
9. **For Gamescope overlays, prefer `--mangoapp` over wrapping the game with MangoHud.** ArchWiki notes traditional MangoHud with gamescope is not supported and recommends Gamescope's `--mangoapp`, which runs MangoHud over Gamescope instead of the underlying application. This is useful for compositor-level FPS/GPU telemetry without perturbing the game process as much. [ArchWiki Gamescope](https://wiki.archlinux.org/title/Gamescope)
10. **MangoHud can produce launch-scoped telemetry logs.** MangoHud's README/config docs require `output_folder` for logging; toggling logging creates a timestamped file with the game name in that folder. Use a per-launch config via `MANGOHUD_CONFIG`/config file that sets `output_folder`, `log_interval`, and optional autostart if supported by the packaged version; emit `telemetry_log_started` on file creation and `first_frame_observed` when FPS/frame samples appear. [MangoHud README](https://github.com/flightlessmango/MangoHud/blob/master/README.md?plain=1), [MangoHud config](https://github.com/flightlessmango/MangoHud/blob/master/data/MangoHud.conf)
11. **FEX observability is configuration-file based and should remain diagnostic by default.** FEX's config system is generated from JSON config definitions, and public examples/docs refer to `~/.fex-emu/Config.json` sections such as `Debug` and `Logging` with keys including `LogLevel`, `SilentLog`, and `OutputLog`; recent release notes mention `OutputLog` behavior changes. Treat FEX logs as opt-in diagnostic enrichment for x86-on-ARM launches, and rely on the supervised FEX/proton process exit for `game_exited`/`crashed`. [FEX config wiki](https://wiki.fex-emu.com/index.php/Config), [FEX Config.json.in reference](https://github.com/FEX-Emu/FEX/blob/main/FEXCore/Source/Interface/Config/Config.json.in), [FEX releases](https://github.com/FEX-Emu/FEX/releases)

## Recommended event mapping
- `runtime_prepare_started`: before invoking Steam/Proton runtime wrapper; include appid, compat tool, runtime name, env toggles enabled.
- `runtime_prepare_log_available`: detect Steam Runtime log/diagnostic files under `~/.steam/root/logs` or controlled log dir; include path, size, mtime.
- `game_process_started`: supervised child PID/start timestamp from the launcher, not log parsing.
- `compositor_ready`: Gamescope `--ready-fd` notification.
- `window_ready`: best-effort Xwayland window appears/maps via `xwininfo`/`xprop`; include display/window id/title/class when available.
- `graphics_backend_detected`: DXVK/VKD3D log file appears; classify by filename (`d3d9`, `d3d11`, `dxgi`, VKD3D/D3D12) and parse adapter lines only defensively.
- `gpu_device_selected`: VKD3D/DXVK/Vulkan loader logs or MangoHud samples indicate GPU/driver; include confidence level.
- `first_frame_observed`: first MangoHud sample with FPS/frame timing or Gamescope stats if available.
- `game_exited`: launcher wait status; include exit code/signal/core-dump flag if available.
- `crash_suspected`: non-zero exit, signal, Wine/Proton exception markers, or crash dialog/window; keep as derived evidence, not the primary exit fact.

## Gaps
- Exact Proton log line formats are not a stable public contract; parse them only as heuristic enrichment and keep raw logs for support bundles.
- Gamescope stats file/socket behavior needs local validation against the packaged version in Korri's target environment; `--ready-fd` is the strongest documented readiness surface found.
- FEX logging behavior appears to have changed across releases; verify the installed FEX version's accepted `OutputLog` values before wiring automated capture.
- Window readiness under pure Wayland clients remains compositor-specific; Xwayland observation is practical for Proton/Wine but not a universal Wayland contract.
